# 路线规划

## 概述

路线规划是 product-manager 的核心决策能力。当用户提出新的功能想法或需要明确下一步方向时，执行路线规划分析，综合以下信息源给出优先级建议。

## 信息收集

分析前必须读取以下信息源（按优先级排列）：

### 必读信息源

1. **竞品调研**：`docs/product_research/` 中与目标功能模块相关的竞品文档
   - 竞品做了什么、怎么做的、用户反馈如何
   - 我们缺少哪些竞品已有的关键功能

2. **现有 wiki**：通过 `Skill("llm-wiki")` 查阅相关功能域文档
   - 当前项目已有哪些能力
   - 目标功能与现有功能的关联和潜在冲突

3. **当前进展**：`docs/product_manager/progress.md`（如存在）
   - 哪些功能正在开发中
   - backlog 中已有的待办项

4. **用户输入**：用户本次提出的想法、约束、优先级偏好

### 可选信息源

- `docs/product_manager/roadmap.md` — 已有路线图
- `docs/product_manager/decisions/` — 历史决策记录
- `PRODUCT.md` — 产品定位信息

## 分析框架

### 维度一：用户价值

| 指标 | 说明 |
|------|------|
| 覆盖用户群 | 功能能覆盖多少用户？核心用户 / 边缘用户？ |
| 使用频率 | 高频刚需 vs 低频辅助 |
| 痛点程度 | 解决的是「很痛但能忍」还是「有更好没也过」 |

### 维度二：竞品差距

| 指标 | 说明 |
|------|------|
| 竞品覆盖率 | 竞品中多少产品有此功能？ |
| 差异化机会 | 能否做得比竞品更好？而不是简单照搬 |
| 时间窗口 | 现在不做会不会被拉开差距？ |

### 维度三：实现可行

| 指标 | 说明 |
|------|------|
| 技术依赖 | 是否需要新的技术能力/基础设施？ |
| 端上工作量 | 各端合计工时的粗略估计（用 S/M/L/XL 表示） |
| 阻塞风险 | 是否依赖其他功能？是否被其他功能依赖？ |

### 维度四：产品战略

| 指标 | 说明 |
|------|------|
| 与产品定位的契合度 | 是否偏离产品核心方向？ |
| 阶段性目标 | 当前阶段是拉新？留存？变现？这个功能贡献什么？ |

## 输出

### 决策记录

每次分析输出一份决策记录，保存到 `docs/product_manager/decisions/YYYY-MM-DD-<topic>.md`，包含：

```
# 决策记录：<主题>

- 日期：YYYY-MM-DD
- 触发：用户输入 / 定期复盘 / feature-workflow 完成

## 背景

<!-- 当前产品状态、用户提出的想法、已有进展 -->

## 分析

### 候选方向

| 编号 | 功能 | 用户价值 | 竞品差距 | 实现可行 | 产品战略 | 综合评分 |
|------|------|---------|---------|---------|---------|---------|
| F-01 | | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |

### 建议优先级

1. **P0（立即启动）**：<功能名> — <理由>
2. **P1（下一迭代）**：<功能名> — <理由>
3. **P2（后续规划）**：<功能名> — <理由>
4. **暂不推进**：<功能名> — <理由>

## 决策

<!-- 明确决定：做什么、不做做什么、为什么 -->

## 待澄清

<!-- 需要用户确认的事项 -->
```

### 更新文档

分析完成后，更新以下文档：
- `roadmap.md`：如有路线变化
- `backlog.md`：新增/调整功能项优先级
- `progress.md`：无需更新（功能尚未进入开发）

## 用户确认

路线规划分析完成后，向用户呈现建议摘要并等待确认：

> 「📊 基于竞品分析、现有 wiki 和当前进展，建议按以下优先级推进：」
> 「1️⃣ P0：<功能名> — <简要理由>」
> 「2️⃣ P1：<功能名> — <简要理由>」
> 「…」
> 「是否按此优先级推进？或你有其他考虑？」

不代替用户做最终决策——路线规划的产出是「建议」，最终决策权在用户。
