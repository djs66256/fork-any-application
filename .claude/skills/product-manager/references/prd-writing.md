# PRD 撰写规范

## 定位

将模糊的功能想法转化为精确的、可执行的 PRD 文档。PM 阶段的 PRD 是**精简版**，只关注「做什么、为什么、给谁用」。技术细节、非功能性需求、异常处理细节留给 feature-workflow spec 阶段补充。

## 信息准备

撰写 PRD 前，必须完成信息收集：

1. **读取竞品资料**：`docs/product_research/` 中相关模块的功能文档，了解竞品怎么做
2. **查阅 wiki**：通过 `Skill("llm-wiki")` 查阅相关功能域，避免与现有能力冲突
3. **读取进展**：`docs/product_manager/progress.md` 和 `backlog.md`，了解是否有依赖/冲突的功能
4. **澄清模糊点**：如果用户描述中存在以下模糊情况，必须先向用户确认：
   - 功能边界不清晰（"做一个类似 XXX 的功能"——XXX 具体指什么？）
   - 用户角色不明确（谁用这个功能？）
   - 关键交互未描述（用户怎么触发？怎么退出？）

## PRD 模板

使用 `assets/prd-template.md` 作为模板。PRD 与 feature-workflow spec 的区别：

| 维度 | PRD（本 skill） | Spec（feature-workflow） |
|------|----------------|------------------------|
| 关注点 | 做什么、为什么、给谁用 | 怎么实现、技术方案、API 设计 |
| 读者 | 产品决策 | 开发为主 |
| 粒度 | 完整功能（可能跨多端） | 单次开发交付 |
| 技术细节 | 无 | 有（API、数据模型、架构、非功能性需求、异常处理） |
| 验收标准 | 业务验收（用户视角） | 技术验收（实现视角） |

### PRD 精简原则

PM 阶段的 PRD 应该简洁、聚焦，目的是让决策者快速理解功能全貌并做出判断。以下章节在 **PM 阶段不需要**（留给 spec 阶段）：

| 不需要的章节 | 原因 |
|-------------|------|
| 详细数据模型/数据关系 | 技术实现细节，spec 阶段由开发补充 |
| 非功能性需求（性能指标、安全要求） | 技术约束，spec 阶段定义 |
| 详细边界与异常处理表 | 只在核心流程中标注关键异常即可，完整异常覆盖是 spec 的职责 |
| 兼容性与迁移方案 | 技术实现细节 |
| 术语表 | 如有需要，直接在使用处解释，不必单独章节 |

PRD 应该能在一页内让读者理解：**为什么要做、做什么、不做什么、给谁做、涉及哪些端**。

### 产物路径

PRD 产物放在 `docs/product_manager/prd/YYYY-MM-DD-<feature-slug>/` 下，日期为创建日期：

```
docs/product_manager/prd/2026-07-23-homepage-feed/
├── prd.md
└── subtasks.md
```

## 子任务拆分

### 拆分原则

PRD 撰写完成后，继续拆分为可独立开发的子任务。原则：

1. **可独立交付**：每个子任务完成后应产生可验证的增量价值（不是「做了 50% 的 UI」，而是「用户可以看到并操作 XX」）
2. **每端 ≤5 人日**：这是硬约束。估算超出时必须继续拆分。拆分方向：
   - 按交互路径拆（先做核心链路的「最小可用」，再补辅助功能）
   - 按用户故事拆（先做 P0 故事，再 P1、P2）
   - 按数据链路拆（只读展示 → 用户输入 → 数据持久化 → 后台管理）
3. **跨端独立**：每个端的子任务应能各自独立开发，不互相阻塞
4. **有先后约束时按阶段拆**：若后端 API 是各端前置依赖，则后端先作为一个子任务

### 工时估算参考

| 复杂度 | 特征 | 参考工时 |
|--------|------|---------|
| S | 纯 UI 展示、简单数据读取、配置变更 | 1-2 人日/端 |
| M | 含表单交互、列表操作、基础 CRUD | 2-3 人日/端 |
| L | 多步骤流程、复杂状态管理、多端协同 | 3-5 人日/端 |
| XL | 超过 5 人日，必须继续拆分 | 拆到 M/L 为止 |

### 输出到 subtasks.md

使用 `assets/subtasks-template.md` 输出子任务清单。子任务编号使用 `ST-01`~`ST-NN` 形式。

## 用户确认

PRD 和子任务拆分完成后，向用户呈现摘要：

> 「📋 PRD 撰写完成：<功能名>」
> 「📊 工时评估：Backend X 人日 + iOS X 人日 + Android X 人日 + Web X 人日」
> 「📦 子任务：共 N 个（ST-01 ~ ST-NN），预计 X 个迭代」
> 「🔍 是否进入 PRD Review？或需要调整？」

用户确认后，进入 PRD Review 阶段。
