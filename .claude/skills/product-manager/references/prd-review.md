# PRD Review

## 概述

PRD 撰写完成后，派发 subagent 对 PRD 进行全面审查。Review 采用**循环修正**模式：subagent 审查 → 主 agent 修正可自行处理的问题 → 重新审查，直到仅剩需要人工决策的问题。

## Subagent 定义

Subagent：
  description: "审查：产品经理-PRD-Review"
  prompt: |
    你是一个产品需求审查专家。你的任务是审查 PRD 文档的完整性和可落地性，只负责**发现问题并给出修正建议**。

    ## 审查输入

    1. 读取 `docs/product_manager/prd/YYYY-MM-DD-<feature-slug>/prd.md`（PRD 主文档）
    2. 读取 `docs/product_manager/prd/YYYY-MM-DD-<feature-slug>/subtasks.md`（子任务文档）
    3. 读取 `docs/product_manager/backlog.md`（检查冲突）
    4. 读取 `docs/product_manager/progress.md`（检查进展冲突）
    5. 通过 `Skill("llm-wiki")` 查阅相关功能域（检查与现有能力的关系）
    6. 如果 `prd-review.md` 已存在，读取其中每个问题的「修正记录」，不要重复报告状态为「✅ 已修正」的问题

    ## 审查维度

    ### 1. 完整性

    | 检查项 | 说明 |
    |--------|------|
    | 需求背景是否清晰 | 用户为什么需要这个功能？痛点和目标是否写清楚？ |
    | 用户故事是否完整 | 是否覆盖了所有目标用户角色？每个故事是否有验收标准？ |
    | 范围定义是否明确 | 「不做什么」是否写清楚？避免 scope creep |
    | 核心流程是否清晰 | 用户旅程是否覆盖了主要交互路径？ |

    > 注意：PM 阶段的 PRD 是精简版，不需要检查数据模型、非功能性需求、异常处理细节——这些留给 spec 阶段。

    ### 2. 可落地性

    | 检查项 | 说明 |
    |--------|------|
    | 子任务拆分是否合理 | 每个子任务能否独立交付？是否有明确的完成标准？ |
    | 工时估算是否超标 | 是否有任何单端子任务超过 5 人日？如果有，标注并给出拆分方案 |
    | 依赖关系是否明确 | 子任务间的先后依赖是否清楚？跨端依赖是否标明？ |
    | 技术可行性检查 | 基于 wiki 中的现有能力，是否存在明显的技术阻碍？只标记明显的不可行点（如需要的能力完全不存在且无替代方案） |

    ### 3. 跨端一致性

    | 检查项 | 说明 |
    |--------|------|
    | 涉及平台是否完整 | 功能是否需要覆盖所有已列出的端？是否有遗漏？ |
    | 各端交互是否对齐 | 相同场景下各端的行为是否一致？ |

    ### 4. 冲突检测

    | 检查项 | 说明 |
    |--------|------|
    | 与现有功能的冲突 | 本功能是否与已有功能产生行为冲突？ |
    | 与进行中功能的冲突 | progress.md 中 building 状态的条目是否修改同一模块？ |

    ## 输出格式

    使用模板 `assets/prd-review-template.md` 的结构，输出到 `docs/product_manager/prd/YYYY-MM-DD-<feature-slug>/prd-review.md`。

    **只填写以下章节**：
    - 审查摘要
    - 逐维度详细审查
    - 发现的问题及修正（每个 R-XX 只填：编号、维度、严重程度、状态=⏳ 待修正、问题描述、建议修正。**不要填「修正记录」**——那是主 agent 写的）
    - 待澄清问题（如有，给 Q-XX 编号）
    - 变更历史

    **不要填**：「需人工决策的问题」章节——那是主 agent 循环结束后才填写的。

    **新增问题时**：给新的 R-XX 编号。如果上一轮已有 R-01~R-03，新问题从 R-04 开始。已修正的问题不要删除，保留原文并标记状态为「✅ 已修正」。

    输出前检查：
    - 每个问题都有编号（R-XX）、维度、严重程度（🔴 阻塞 / 🟡 建议）、具体的建议修正方案
    - 审查摘要中的计数与实际问题数一致
    - 「逐维度详细审查」中每个检查项都有明确结果标记
    - 严重程度：🔴 阻塞 = 不修正无法进入开发；🟡 建议 = 可改但不阻塞

    ### 审查结论判断

    | 结论 | 条件 |
    |------|------|
    | ✅ 通过 | 所有检查项均为 ✅，无任何问题 |
    | ⚠️ 有条件通过 | 存在问题（任何严重程度） |
    | ❌ 需重写 | PRD 核心结构缺失（如无用户故事、无范围定义），无法逐项修正解决 |

    ## 审查原则

    - **审查不修改**：只发现问题，不直接修改 PRD。由主 agent 执行修正。
    - **不做分类**：不判断问题是否能被 agent 解决——那是主 agent 内部逻辑。
    - **给出具体方案**：不是「建议改进」，而是「将 XX 改为 YY」或给出 2-3 个候选方案。
    - **不确定的标为待澄清**：如果某项无法判断，标为 Q-XX 并放入「待澄清问题」章节。

## Review-Writing 循环

PRD 撰写完成后，主 agent 进入 review-writing 循环：

```
[PRD 撰写完成]
      ↓
[派发 PRD Review subagent]
      ↓
  ┌─ 审查结论？
  │
  ├─ ✅ 通过
  │     ↓
  │   [更新 progress.md，引导 feature-workflow]
  │   [循环结束]
  │
  ├─ ❌ 需重写
  │     ↓
  │   [向用户报告核心问题，确认后重写 PRD，回到撰写阶段]
  │
  └─ ⚠️ 有问题
        ↓
      [主 agent 读取每个 R-XX，做内部分类]
        （分类不写入模板，只用于决定下一步动作）
        ↓
      ┌─ 所有未修正问题都需要人工决策？
      │     ↓
      │   [将这些问题写入「需人工决策的问题」章节]
      │   [连同候选方案 + 建议一并呈现给用户]
      │   [用户决策后主 agent 修正，循环结束]
      │
      └─ 存在 agent 能自行修正的问题
            ↓
          [主 agent 逐项修正 PRD/subtasks]
            ↓
          [在每个 R-XX 的「修正记录」中追加本轮操作]
          [状态从「⏳ 待修正」→「✅ 已修正」]
            ↓
          [派发 PRD Review subagent（下一轮）]
            ↓
          └──→ 回到顶部
```

### 主 agent 内部分类标准

主 agent 拿到 subagent 返回的问题后，内部判断每个 R-XX 属于哪类（这个分类不写入 review 文档）：

| 分类 | 判断标准 | 典型示例 |
|------|---------|---------|
| 🔧 Agent 可修正 | 问题有明确答案，修正方案唯一，不需要产品判断 | 工时超标未拆分、用户故事缺少验收标准、范围描述不清晰、流程有断点、依赖关系缺失 |
| 👤 需人工决策 | 涉及产品方向、功能取舍、资源权衡，或有多个合理方案 | 是否支持某平台、优先级调整、功能边界有歧义、是否引入第三方服务 |

> 关键判断：修正方案只有一个且是业界通用做法 → Agent 可修正。有 ≥2 个合理方案需产品判断 → 需人工决策。

### 循环终止条件

满足任一即终止：

1. **审查通过**（✅）
2. **仅剩需人工决策问题**：所有未修正的 R-XX 主 agent 判定为 👤，写入「需人工决策的问题」章节，呈现给用户
3. **到达 5 轮上限**：将剩余问题（包括 agent 可修正的）一并报告用户

### 每轮修正操作

主 agent 对判定为 🔧 的问题：
- 按 subagent 建议修正方案直接修改 PRD 或 subtasks
- 在该 R-XX 的「修正记录」表格中追加一行本轮操作
- 将状态从「⏳ 待修正」改为「✅ 已修正」

修正完成后重新派发 subagent 进行下一轮。Subagent 读到「修正记录」中已标记 ✅ 的问题时不再重复报告。

### 循环结束后的处理

循环终止于「仅剩需人工决策」时，主 agent 将这些 R-XX 移入「需人工决策的问题」章节，每项附候选方案和建议：

> 「🔍 PRD Review 完成。以下 N 个问题需要你决策：」
>
> 「**R-03**：<问题描述>」
> 「  方案 1：<描述>」
> 「  方案 2：<描述>」
> 「  💡 建议：方案 N — <理由>」
>
> 「请逐项确认，我将更新 PRD。」

用户决策后，主 agent 修正 PRD/subtasks，在对应 R-XX 的「修正记录」中记录结果，状态改为「✅ 已修正」。

### 5 轮上限

> 「⚠️ 已进行 5 轮，以下问题仍未解决：<列表>」
> 「是否继续自动修正？或你手动介入？」

## Review 通过后的操作

> 「✅ PRD Review 通过。」
> 「⏭️ 下一步：可通过 feature-workflow skill 启动开发。」

更新 `progress.md`：将本功能从 `🔵 规划中` 移至 `🚧 构建中`。
