# 竞品分析规划指南

在开始采集之前，需要明确分析范围、拆分子任务、制定采集方案。

## 0. 检查已有进度

在确认分析范围之前，先读取 `docs/product_research/PROGRESS.md` 了解目标模块的已有采集和进度。

1. 如 `PROGRESS.md` 不存在（首次使用），按以下方式初始化：
   - 遍历 `captures/` 下所有目录，读取每个 `capture.md` 中的「采集信息」表提取功能模块
   - 检查磁盘状态：有 `analysis.md` → 采集✅ 分析✅ 成文✅；`assets/` 下有文件 → 采集✅；否则 → 采集 todo
   - 按功能模块分组、按 capture 路径排序，生成完整的 `PROGRESS.md` 文件
2. 筛选目标功能模块的所有行，向用户呈现已有进度摘要。
3. 对于状态为 `doing` 的采集，向用户确认是否为上次会话中断遗留，决定等待/重采/标记失败。
4. 根据已有覆盖情况，判断是否需要新增采集或可复用已有产物，向用户提出建议。
5. 用户确认后再进入下一步分析范围确认。

## 1. 确认分析范围

从用户描述中提取以下要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| 目标竞品 | 要分析哪个应用 | 见 PRODUCT.md |
| 功能模块 | 针对哪个业务功能 | 首页推荐流、播放器、搜索、登录注册 |
| 分析深度 | 覆盖的维度 | 首屏加载 / 完整交互流程 / 异常边界 |
| 目标平台 | mobile / web | mobile（默认） |

分析深度的典型层次（由浅到深）：

| 层次 | 覆盖内容 | 适用场景 |
|------|---------|---------|
| **首屏快照** | 单页面截图 + UI 描述 | 快速了解某个页面的布局 |
| **交互流程** | 完整操作链路 + 页面跳转关系 | 理解核心功能的使用方式 |
| **异常边界** | 空状态、错误处理、网络异常、登录过期 | 覆盖产品健壮性 |

向用户确认范围和分析深度后再进入采集。如果用户没有明确说明深度，默认按「交互流程」层次执行。

## 2. 划分子任务

大范围分析（如「爬一下完整首页交互」）应拆分成多个子任务，逐个执行。每个子任务对应一次「采集→分析→成文」循环，最终汇总为一篇完整的业务功能文档。

### 拆分原则

每个子任务是一个**独立的用户操作路径**，单次采集只走一条路径，避免一次性覆盖大范围。

- **一次一个路径**：每个子任务 = 一个明确的起点 → 一条连续操作链路 → 一个终点。例如不是「播放器所有交互」，而是拆为「点击卡片进入播放器」「播放器控制栏交互」「播放器横竖屏切换」等独立路径。
- **路径有明确边界**：能说清楚从哪个页面/状态开始、经过哪些操作、到哪个页面/状态结束。
- **路径之间独立**：即使共享同一设备，每条路径的起点和终点明确，互不嵌套。
- **单路径步骤数控制在 5-8 步以内**：步骤过多说明路径不够聚焦，应继续拆分。

### 示例：播放器模块拆分

```
播放器模块
├── 点击视频卡片 → 进入播放器（进入路径）
├── 播放页 UI 首屏（静态布局）
├── 控制栏唤出/隐藏 + 暂停/播放 + 进度拖拽 + 倍速（控制栏路径）
├── 竖屏 → 横屏 → 竖屏（横竖屏路径）
├── 播放器 → 退出回到首页（退出路径）
└── 播放器空状态 / 错误状态（异常路径）
```

> 每条路径独立预制一份采集文档，独立的一次采集。

### 执行顺序

- **采集阶段不可并行**：所有采集 subagent 共享同一设备/模拟器，必须**逐个串行**执行，按子任务编号顺序派发。
- **分析阶段可高度并行**：采集全部完成后，分析子任务可以并发执行（见 SKILL.md 阶段 3）。

## 3. 制定采集方案

对每个子任务，明确：

| 要素 | 说明 |
|------|------|
| **操作序列** | 从哪个页面开始，按什么顺序操作，到哪个状态结束 |
| **截图时机** | 每步后截图？仅关键帧？需要标注什么？ |
| **录屏需求** | 动画、转场、加载过渡类操作必须录屏 |
| **预计耗时** | 粗略估计，用于规划并行策略 |

### 判断是否需要录屏

| 场景 | 是否需要录屏 |
|------|------------|
| 静态页面/布局 | ❌ 截图即可 |
| 页面转场动画 | ✅ 必须录屏 |
| 滚动/滑动行为 | ✅ 必须录屏 |
| Loading → 内容过渡 | ✅ 必须录屏 |
| 按钮点击反馈 | 可选，截图通常够用 |

## 4. 预制采集文档

对每个子任务，按 `assets/capture-template.md` 模板预制采集文档，保存到 `captures/<日期>-<描述>/capture.md`。

预制内容包括：
- 采集信息（竞品名、版本、包名、频道、采集方案、功能模块、采集范围）
- 命令参考（频道对应的命令参考文件）
- **完整操作序列**：每个步骤的「操作」「命令」「截图路径」「观察要点」
- 录屏需求（是否需要、覆盖范围）

**不填**的内容（留给采集 subagent 回填）：
- 每步骤的「观察」「截图文件」
- 产物清单
- 采集日志
- 异常记录

### 输出给用户确认

向用户呈现分析计划概览 + 各采集文档路径，确认后进入采集。

```markdown
## 分析计划

- **竞品**：{{名称}}
- **平台**：{{mobile/web}}
- **分析深度**：{{层次}}

### 子任务列表

| # | 子任务 | 采集文档 | 步骤数 | 录屏 | 预计耗时 |
|---|--------|---------|--------|------|---------|
| 1 | {{名称}} | `captures/{{日期}}-{{描述}}/capture.md` | N 步 | 是/否 | ~N min |
| 2 | {{名称}} | `captures/{{日期}}-{{描述}}/capture.md` | N 步 | 是/否 | ~N min |

确认后开始采集。
```

用户确认后，按子任务列表逐个派发采集 subagent，每个只传采集文档路径。

## 5. 更新进度文件

用户确认分析计划后，在 `docs/product_research/PROGRESS.md` 中为每个新建的采集文档追加一行：

- **采集文档路径**：相对于 `docs/product_research/` 的路径
- **功能模块**：从采集文档的「采集信息」表中提取
- **采集**：`doing`（即将派发采集 subagent）
- **分析、成文、Review**：`todo`

如 `PROGRESS.md` 不存在则先创建（包含表头和说明注释）。

**修正已有行**：如果目标模块已有相同采集文档路径的行（例如之前状态为 `todo` 待采集），则将对应行的采集状态从 `todo` 改为 `doing`，不重复追加。

**维护最后更新时间**：每次修改 `PROGRESS.md` 后，更新文件顶部的「最后更新」时间戳为当前时间。
