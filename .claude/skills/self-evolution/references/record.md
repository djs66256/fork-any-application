# 记录流程详解

## 触发方式

仅用户主动触发，不做自动提示。触发词包括：

- "记录一下"、"记录这个问题"、"记一下"
- "回顾会话"、"回顾一下"、"看看有什么问题"
- "有哪些可以改进的"、"总结一下问题"
- "这个应该进 evolution"

## 记录范围

回顾会话时，从以下维度审视：

1. **纠正类**：用户在本会话中纠正过 agent 的哪些行为？（"你应该先读 wiki"、"不要直接改那个文件"）
2. **卡顿类**：哪些步骤花费了异常多的时间？（review 循环超过 3 轮、反复重试失败）
3. **重复类**：哪些上下文每次会话都要重新说明？（模块约定、特殊规则、命名偏好）
4. **缺失类**：哪些操作缺少 skill/subagent 覆盖？（每次都要手动执行的固定流程）
5. **矛盾类**：agent 的行为和某条文档规则冲突？或者两条规则本身互相矛盾？
6. **返工类**：哪些产出需要反复修改才能通过？（用户多次驳回、同一产物改了 3 版以上）
7. **记忆查找类**：哪些信息查找花费了异常多的时间？（搜了很多文件才定位、读了大量无关内容才发现目标）

## 记录内容

每条记录只包含事实描述，不包含建议和目标（那是进化阶段的工作）。详细模板见 [assets/record-template.md](../assets/record-template.md)。

| 字段 | 说明 |
|------|------|
| **类型** | 见下方「记录类型」 |
| **严重程度** | blocker / repetitive / friction / observation |
| **改进目标** | 应该改的具体文件路径（项目相对路径），用于后续按目标分组触发进化。`skill-missing` 类型写「待新建」，`other` 类型写「待分析」 |
| **上下文** | 当时在执行什么任务、哪个 skill 的哪个阶段 |
| **问题描述** | 具体发生了什么、为什么这是个问题 |
| **期望行为** | 理想情况下应该怎么运作 |

## 记录类型

| 类型 | 含义 | 示例 |
|------|------|------|
| `skill-design` | Skill 设计缺陷：流程不合理、步骤缺失、subagent prompt 不精确 | feature-workflow 的 design-review 每次都漏检同一类问题 |
| `skill-missing` | 缺少 Skill：某高频操作没有对应 skill 封装 | 每次都要手动执行「查看 git 变更并生成 changelog」 |
| `claude-md` | CLAUDE.md 规则问题：不清、过时、矛盾、缺失 | 根 CLAUDE.md 说"禁止硬编码"，但某端 CLAUDE.md 示例用了硬编码 |
| `memory-gap` | 短期记忆缺失：上下文每次都要重新说明 | 用户每次新会话都要讲一遍某模块不走 REST API 而是用 WebSocket |
| `process-bottleneck` | 流程卡点：阶段设计导致效率低下 | coding 阶段 build 失败后 subagent 都要重新读代码而非从上次上下文继续 |
| `rework` | 返工：产出需要反复修改 | 用户在同一阶段驳回了 3 次，每次都是类似的问题没修好 |
| `memory-lookup` | 记忆查找：查找信息花费了异常多的时间 | 找了 5 个文件、读了 200 行才定位到某个功能的具体实现 |
| `tool-experience` | 工具使用体验：权限弹窗、命令失败、MCP tool 不可用 | 某 MCP tool 的入参格式文档与实际不一致 |
| `coordination` | 多 skill/subagent 协作：信息丢失、职责重叠、产物格式不兼容 | product-manager 的 PRD 和 feature-workflow 的 spec 模板有大量重复字段 |
| `other` | 以上都不归类的问题 | — |

### 类型分类决策

优先选择**最具体的类别**。以下映射表辅助归类：

| 回顾维度 | 最可能对应的记录类型 |
|---------|-------------------|
| 纠正类（用户纠正 agent 行为） | `skill-design`、`claude-md`、`memory-gap` |
| 卡顿类（步骤花费异常多时间） | `process-bottleneck` |
| 重复类（上下文每次重新说明） | `memory-gap` |
| 缺失类（缺少 skill/subagent） | `skill-missing` |
| 矛盾类（规则冲突） | `claude-md` |
| 返工类（产出反复修改） | `rework` |
| 记忆查找类（查找信息耗时） | `memory-lookup` |

决策顺序：

1. 先看是不是 `skill-design`、`skill-missing`（改或新建 skill）
2. 再看是不是 `claude-md`（改 CLAUDE.md 系列）
3. 再看是不是 `rework`、`memory-lookup`（改流程/信息组织）
4. 再看是不是 `coordination`（跨 skill 协作）
5. 最后看是不是 `process-bottleneck`、`tool-experience`、`memory-gap`
6. 都不匹配 → `other`

## 严重程度

按决策树判定：

```
问：这个问题是否阻断了当时的流程？
├─ 是 → blocker（如：workflow 脚本报错无法继续）
└─ 否 → 问：这个问题是否在本次会话中出现了 ≥2 次？
         ├─ 是 → repetitive（如：每次 build 都失败需要手动改配置）
         └─ 否 → 问：是否可预判会在后续会话中反复出现？
                  ├─ 是 → repetitive（如：某模块的关键约定没写入文档，每次新会话都会踩坑）
                  └─ 否 → 问：这个问题是否影响了产出质量或额外浪费了 token/时间？
                           ├─ 是 → friction（如：subagent 产出格式对但字段命名不一致）
                           └─ 否 → observation（如：注意到某 reference 文档可以补充内容）
```

| 级别 | 含义 | 进化优先度 |
|------|------|-----------|
| **blocker** | 阻断：导致流程完全无法继续，每次必现 | 立即建议进化 |
| **repetitive** | 重复：每次都要人工纠正，浪费大量 token | 优先进化 |
| **friction** | 摩擦：能用但体验不好，偶尔出问题 | 按阈值进化 |
| **observation** | 观察：潜在改进点，还不确定是不是问题 | 积累观察，等待更多证据 |

## 常见误区

### 不要记录

- **一次性错误**：agent 偶尔读错文件、理解偏差——除非反复出现
- **用户业务需求本身**：用户说"倍速功能要加 0.75x"——这是 feature 需求，不是 harness 进化素材
- **外部系统偶发故障**：GitHub API 超时、MCP server crash——除非 harness 设计需要容错
- **主观偏好**：用户说"这个变量名我不喜欢"——除非涉及命名规范缺失

### 容易忽视但应该记录

- **静默成功**（看起来没问题但实际有隐患）：subagent 自己修正了错误但花了大量时间
- **用户放弃了某项功能**：用户说"算了不用 XX 了"——说明 XX 的触发条件或行为有问题（归类为 `skill-design`）
- **跨 session 模式**：用户连续多个会话都提到同一个问题——单次看可能不明显
- **文档与实际不一致**：CLAUDE.md 说某个目录有文件，但实际不存在

## 写入流程

1. 主 agent 回顾会话（不用 subagent）
2. **首次初始化**：
   - 如果 `docs/evolution/` 目录不存在，创建之
   - 如果 `docs/evolution/index.md` 不存在，按 [assets/index-template.md](../assets/index-template.md) 创建，填入表头即可（无数据行）
3. **评估短期记忆利用情况**：
   - 检查 `docs/short_memory.md` 是否存在且有内容
   - 如果存在：回顾本次会话中是否读取了 short_memory.md？哪几条记忆被用上了？哪几条虽然记录了但没被读取（漏用）？哪几条读了但信息已过时或不准确？
   - 在 record.md 中写入「短期记忆利用评估」章节
   - 如果 short_memory.md 不存在或为空，跳过此步
4. 如果**没有发现任何值得记录的问题，且短期记忆评估也无异常**，不创建文件，直接告知用户「本次会话未发现需要记录的问题」
5. 如果有问题或短期记忆评估有发现：
   - 确定会话名称：用当前核心任务命名（如 `fix-auth-bug`、`design-player-speed`）
   - 创建目录 `docs/evolution/<YYYY-MM-dd>-<session-name>/`
   - 按 [assets/record-template.md](../assets/record-template.md) 创建 `record.md`
   - 更新 `docs/evolution/index.md`，为每条记录新增索引行（按 [assets/index-template.md](../assets/index-template.md) 的格式）
   - 同步更新 `docs/short_memory.md` 中对应条目的利用情况
   - 统计各严重程度数量，向用户报告
6. 检查同一改进目标下「待进化」记录是否 ≥ 3 条，如果是则提示用户可开启进化

## 产物目录结构

```
docs/evolution/
├── index.md                          # 素材总索引
├── <YYYY-MM-dd>-<session-name>/      # 按会话组织
│   └── record.md                     # 本次会话的记录条目
└── ...
```

## 短期记忆

`docs/short_memory.md` 用于存放「每次会话都需要重新说明」的上下文。

### 格式

```markdown
# 短期记忆

## <主题>

- **上下文**：<在什么场景下需要这段记忆>
- **内容**：<需要记住的信息>
- **来源**：<来自哪次会话/哪个 record>
- **记录时间**：YYYY-MM-DD
- **利用次数**：N
- **漏用次数**：N
- **具体利用记录**：
  - YYYY-MM-DD：<在什么任务中用了这条记忆，解决了什么问题>
  - ...
- **状态**：有效 / 过时 / 待验证
```

### 字段说明

| 字段 | 说明 |
|------|------|
| **利用次数** | 这条记忆在历次会话中被读取并帮助到了 agent 的总次数 |
| **漏用次数** | 这条记忆存在但会话中 agent 没有读取它，导致重复犯错的次数 |
| **具体利用记录** | 每条记录：日期 + 在什么任务中用了这条记忆 + 解决了什么问题。用于评估记忆的实际价值，不是"有没有用"而是"在什么场景下起了什么作用" |
| **状态** | `有效`=信息准确仍有价值 / `过时`=信息已不再适用 / `待验证`=本次发现可能过时但不确定 |

### 写入与维护

- 记录流程中发现 `memory-gap` 类型的问题时，将缺失的上下文写入 `docs/short_memory.md`
- 每次记录时，评估已有短期记忆的利用情况，更新利用次数、漏用次数、具体利用记录、状态
- 进化时这些短期记忆应被提升为长期规则（skill reference 或 CLAUDE.md），然后从 short_memory.md 中移除
- `漏用次数 ≥ 3` 或状态为 `过时` 的记忆，进化时应优先处理
