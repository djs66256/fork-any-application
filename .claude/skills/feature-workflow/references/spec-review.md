# 需求 Review Subagent

spec-review 阶段的执行者是一个 **单向 subagent**：它只负责审查和输出报告，不负责修复。主 agent 读取 review 结果后，自行解决所有可自动处理的问题。

## 使用方式

1. spec-writing 阶段完成后，主 agent 派发 spec-review subagent
2. subagent 自行加载 skill、读取 spec.md 和相关 wiki 文档
3. subagent 按审查维度检查，**发现的问题不修复，只记录到 spec-review.md**
4. subagent 完成后，主 agent 读取 `spec-review.md`，逐一解决记录的问题
5. **主 agent 解决所有非人工问题后** → 调用 `workflow.py advance` 推进到 spec-human-review
6. **有遗留问题（需人决策）** → 向用户展示，等用户回复后继续修复
7. 修复过程中如需重新审查，可再次派发 subagent
8. **达到 3 轮上限** → 停止循环，强制上报人工

## 完成标准

- ✅ **达成**：所有非人工决策的问题已被主 agent 解决（spec-review.md 中无非遗留问题）
- ⚠️ **人工介入**：存在 agent 无法决策的问题，已向用户展示
- 🛑 **上限**：修复循环轮次超过 3 轮，强制上报

## Subagent 定义

```
Subagent：
  description: "Review：需求文档-<feature-name>"
  prompt: |
    你是一个需求文档质量审查 agent。你的职责是**发现问题并记录**，不做修复。
    修复工作由主 agent 在读取你的 review 报告后执行。

    ## 准备

    1. 通过 Skill 工具加载 `feature-workflow` skill，指定阶段：`spec-review`，获取模板和规范上下文。
    2. 读取需求文档 `docs/specs/<YYYY-MM-dd>-<name>/spec.md`。
    3. 通过 Skill 工具加载 `llm-wiki` skill，读取相关 wiki 文档作为参考。

    ## 阶段 1：Clarify（扫描模糊点）

    扫描 spec.md 中所有 `[待确认]` 标记，逐一评估：

    - 能从 wiki 中确认的 → 记录为问题，标注「可从 wiki 确认」
    - 能从代码中确认的 → 记录为问题，标注「可从代码确认」
    - 需要产品决策的 → 记录为遗留问题
    - 不影响推进的 → 记录为问题，标注「建议默认值：...」

    全部 `[待确认]` 扫描完成后，进入审查。

    ## 阶段 2：审查维度

    ### 1. 完整性

    检查以下内容是否都已充分描述：

    - [ ] 需求背景：是否清晰说明了"为什么做"和"要解决什么问题"
    - [ ] 用户故事：是否覆盖了所有角色和场景
    - [ ] 验收标准：是否可度量、可测试，没有模糊表述
    - [ ] 边界与异常：是否覆盖了完整的错误处理和边界场景（⚠️ 重点检查，最易遗漏）
    - [ ] 涉及平台：是否明确了各端的改动范围
    - [ ] 非功能性需求：是否考虑了性能、安全、兼容性
    - [ ] 依赖：是否列出了外部依赖及其状态

    ### 2. 边界与错误处理（⚠️ 专项审查）

    逐项检查 spec.md 中"边界与异常"章节是否充分覆盖：

    #### 错误处理流程
    - [ ] 每个关键用户操作是否都有对应的错误处理描述
    - [ ] 错误处理是否覆盖了"错误类型 → 触发条件 → 系统行为 → 用户感知"的完整链路
    - [ ] 至少覆盖以下错误类型：
        - 网络异常（超时、断网、DNS 解析失败）
        - 服务端错误（500、502、503）
        - 数据校验失败（客户端校验 + 服务端校验）
        - 权限不足（未登录、角色不匹配）
        - 操作超时（请求超时、处理超时）
    - [ ] 错误提示对用户是否友好（不暴露技术细节，不展示原始错误码）

    #### 边界场景
    - [ ] 输入边界值是否已考虑（空字符串、超长文本、特殊字符如 emoji/零宽字符/SQL 注入片段）
    - [ ] 并发冲突是否已描述（同一资源同时被修改）
    - [ ] 重复提交/防抖是否已说明
    - [ ] 状态不一致场景是否已覆盖（前置条件不满足时触发操作）
    - [ ] 资源不足是否已考虑（本地存储满、内存不足、配额耗尽）
    - [ ] 数据为空/列表为空/搜索结果为空等空态是否已描述
    - [ ] 极端数据量是否已考虑（超长列表、超大文件）

    ### 3. 一致性（与 wiki 和代码）

    将需求描述与 wiki 中已有功能文档进行交叉比对：

    - [ ] 需求描述是否与 wiki 中已有功能逻辑冲突
    - [ ] 如涉及已有功能变更，是否说明了变更范围和影响
    - [ ] 术语和概念是否与项目已有定义一致
    - [ ] API 路径、数据模型等是否与现有设计一致

    ### 4. 可行性

    - [ ] 需求是否有明显的技术上不可行之处
    - [ ] 是否依赖尚未实现的基础能力
    - [ ] 各端改动估算是否合理

    ### 5. 平台覆盖

    - [ ] 涉及平台的标注是否准确
    - [ ] 各端需求是否有遗漏

    ## 记录原则

    发现问题后**只记录，不修复**。对每个发现的问题标注**严重程度**和**主 agent 是否可自行修复**：

    - 描述不清 → 记录问题，给出修改建议
    - 缺少章节 → 记录问题，给出应补充的内容
    - 与 wiki 不一致 → 记录问题，标注冲突点和代码依据
    - 术语不统一 → 记录问题，给出统一建议
    - 验收标准模糊 → 记录问题，给出可度量标准的改写建议
    - 边界/错误处理遗漏 → 记录问题，给出应补充的场景

    ## 输出

    按 `assets/spec-review-template.md` 模板输出 review 结果到 `docs/specs/<YYYY-MM-dd>-<name>/spec-review.md`。

    ### 问题分类

    对每个发现的问题，标注：

    - **主 agent 可修复**：给出明确的修复建议，主 agent 可直接执行
    - **需人工决策**：记录到「遗留问题」表

    ### 遗留问题标记

    | 编号 | 问题 | 建议 | 状态 |
    |------|------|------|------|
    | H-01 | <问题描述> | <agent 建议> | 待确认 |

    典型需要人工确认的问题：
    - 需求优先级排序（P0/P1/P2）
    - 产品策略相关的设计选择
    - 需要外部协调的依赖问题

    ## 完成标志

    - spec-review.md 已写入
    - 所有发现的问题已分类（主 agent 可修复 / 需人工决策）
    - 每个可修复问题都附带了明确修复建议
```

## 主 agent 后续操作

Subagent 完成后，主 agent 读取 `spec-review.md`，判断：

1. **无遗留问题** → 主 agent 逐一修复所有记录的问题，修复完成后调用 `workflow.py advance` 推进到 spec-human-review
2. **有遗留问题（需人决策）** → 向用户展示遗留问题列表：
   - 用户给出决策后，主 agent 修复所有问题（含遗留问题），修复完成后推进
   - 如需重新审查，再次派发 subagent
3. **有遗留问题（agent 可修复）** → 不应出现此情况。如出现，说明 subagent 分类错误，主 agent 直接修复
4. **达到 3 轮上限** → 停止循环，强制上报人工
