# quality — 错误处理、性能与测试检查

Subagent：
  description: "Code Review：通用-代码质量-<feature-name>"
  prompt: |
    你负责审查 <feature-name> 在 <platform> 端的错误处理、性能问题与测试覆盖。

    注意：你审查的是**跨端通用的质量关注点**，不涉及平台专属问题（如 iOS 内存管理、Android 协程泄漏等，这些在平台专属 subagent 中处理）。

    ## 背景

    特性名称：<feature-name>
    特性目录：docs/specs/<YYYY-MM-dd>-<name>/
    目标平台：<platform>

    ## 准备

    1. 通过 Skill 工具加载 `feature-workflow` skill，获取 code review 规范
    2. 读取共享设计文档 `docs/specs/<YYYY-MM-dd>-<name>/design.md`，了解 API 调用和用户交互流程
    3. 读取 `<platform>/CLAUDE.md` 了解该端错误处理规范（如存在）
    4. 使用 `git diff main --name-only` 获取变更文件列表，仅关注 `<platform>/` 目录下的文件
    5. 逐一读取每个变更文件的内容

    ## 审查维度

    你**只审查以下三大维度**，不涉及其他方面：

    ---

    ### 第一部分：错误处理

    #### 1. 网络请求是否有错误处理

    - 每个网络请求是否都有错误处理逻辑？
    - 是否处理了网络超时、连接失败、DNS 解析失败等场景？
    - 是否处理了 HTTP 错误状态码（4xx、5xx）？
    - 是否有重试逻辑？（非必须，但如果是关键请求，缺少重试应标记）
    - 是否有 loading 状态和错误状态的管理？

    #### 2. 数据解析是否有异常捕获

    - JSON 解析、数据反序列化是否被 try-catch 包裹？
    - 类型转换是否有防御性检查？
    - 来自外部（API、用户输入、文件）的数据是否验证后再使用？
    - 解析失败后是否有降级策略？

    #### 3. 用户操作失败是否有友好提示

    - 当操作失败时，是否向用户展示了可理解的错误信息（而非技术错误堆栈）？
    - 错误提示是否指明了用户可采取的下一步行动？
    - 是否有 toast/弹窗/内联错误信息等 UI 反馈？
    - 是否区分了"用户可自行恢复的错误"和"需要联系支持的错误"？

    #### 4. 边界条件是否处理

    - 空值/undefined/null 是否检查后再访问属性或调用方法？
    - 数组越界是否防护？
    - 字符串截取、数值运算是否有边界保护？
    - 空列表、空结果是否有对应的空状态 UI？
    - 用户输入是否做了长度、格式、范围的校验？

    #### 5. 是否有吞异常（swallow exception）的情况

    - catch 块是否为空？（`catch {}` 或 `catch(e) {}`）
    - catch 块是否只打印了日志但没有做任何处理或上报？
    - catch 块中是否有 `return null` 导致上层无法感知错误？
    - 是否有 `catch` 了过于宽泛的异常类型（如 `catch (Exception e)`）而没有区分处理？
    - 关键错误是否上报到了错误监控系统？

    ---

    ### 第二部分：性能

    #### 6. 是否有不必要的重复计算/渲染

    - 循环内是否有可以提到循环外的重复计算？
    - 是否有在每次渲染/更新中都重新计算但结果不变的表达式？
    - 是否有重复调用同一个纯函数获取相同结果的情况？
    - 前端框架：是否有不必要的组件重渲染？（缺少 memo/useMemo/useCallback 等优化）
    - 是否有在循环中频繁调用 DOM 操作/数据库查询？

    #### 7. 是否有明显的内存泄漏风险

    - 是否有未清除的定时器（setInterval/setTimeout）？
    - 是否有未取消的订阅/监听器（event listener、observer）？
    - 是否有未释放的大对象引用？（缓存无限增长、闭包持有大对象）
    - 是否有在全局作用域持续追加数据的模式（如全局数组只 push 不清理）？
    - 注意：具体平台的内存管理机制（如 iOS ARC、Android GC）由平台专属 subagent 审查

    #### 8. 列表/集合操作是否高效

    - 大数据量列表是否使用了合适的遍历方式？（避免 O(n^2) 嵌套循环）
    - 频繁查找操作是否使用了合适的数据结构？（Map/Set 代替 Array 的 indexOf/find）
    - 列表渲染是否使用了虚拟列表/分页/懒加载？（当列表可能很长时）
    - 是否有对不可变数据结构进行了不必要的全量拷贝？
    - 链式数组操作（filter + map + reduce 等）是否可合并为单次遍历？

    #### 9. 是否有不必要的 I/O 操作

    - 是否有在循环中进行文件读写、数据库查询（N+1 查询问题）？
    - 是否有重复读取同一文件/同一数据源？
    - 是否有不必要的网络请求？（可缓存的数据重复请求）
    - 是否有未做防抖/节流的高频操作（如输入框搜索、滚动事件、resize 事件）？
    - 是否有同步 I/O 阻塞主线程/事件循环的情况？

    ---

    ### 第三部分：测试

    #### 10. 测试是否通过

    - 运行测试命令，检查退出码是否为 0
    - 测试命令从 `<platform>/CLAUDE.md` 获取，如未定义则检查测试文件是否存在
    - 如果有测试失败，记录失败信息

    #### 11. 新增代码是否有对应测试

    - 新增的模块/类/函数是否有对应的测试文件？
    - 关键业务逻辑路径是否被测试覆盖？
    - 边界条件是否有测试？

    #### 12. 测试是否覆盖关键场景

    - 正常路径是否有测试？
    - 异常路径（网络失败、数据为空、输入非法）是否有测试？
    - 边界值是否有测试？

    ## 审查方法

    对每个变更文件：

    **错误处理检查：**
    1. 找出所有网络请求/API 调用点，检查是否被错误处理包裹
    2. 找出所有数据解析/类型转换点，检查是否被 try-catch 包裹
    3. 找出所有用户交互入口，跟踪失败路径，检查用户提示
    4. 对每个属性访问、数组操作、字符串操作，检查是否有空值/边界防护
    5. 检查所有 try-catch 块，确认不是空 catch 或吞异常

    **性能检查：**
    6. 检查循环体：是否有可外提的计算、是否有内嵌 I/O
    7. 检查生命周期/清理逻辑：定时器、监听器、订阅是否有对应的清理代码
    8. 检查数据结构使用：查找是否在数组上进行线性搜索、嵌套循环
    9. 检查 I/O 调用：是否在循环中、是否重复、是否可缓存
    10. 从整体数据流角度审视：数据是否经过了不必要的转换步骤

    **测试检查：**
    11. 运行测试命令，检查是否全部通过
    12. 对比 git diff 中的新增文件和对应的测试文件，检查测试覆盖
    13. 检查测试是否覆盖了正常路径、异常路径和边界条件

    ## 输出格式

    返回结构化 JSON 数组，每个问题一个对象：

    ```json
    [
      {
        "file": "<platform>/path/to/file.ext",
        "line": <line_number_or_null>,
        "severity": "high" | "medium" | "low",
        "title": "问题简要标题（标注属于「错误处理」还是「性能」）",
        "description": "详细描述问题的具体情况和潜在影响",
        "suggestion": "建议如何修复或优化"
      }
    ]
    ```

    ## 严重度判定标准

    **错误处理：**
    - **high**：网络请求无错误处理、空 catch 块吞异常、数据解析无 try-catch 导致可能崩溃
    - **medium**：缺少用户友好提示、边界条件未处理（可能导致 crash 但概率较低）、catch 块仅打印日志不上报
    - **low**：错误提示不够详细、降级策略可优化、异常类型捕获过于宽泛（有兜底处理）

    **性能：**
    - **high**：明显的内存泄漏（定时器/监听器未清理）、N+1 查询、循环内 I/O、O(n^2) 大循环
    - **medium**：不必要的重复计算、可合并的数组操作、缺少防抖/节流、数据结构选择不佳
    - **low**：可优化的数据拷贝、缓存策略可改进、轻微的渲染优化机会

    **测试：**
    - **high**：测试未运行或全部失败、核心功能无任何测试覆盖
    - **medium**：关键新增代码无测试、异常路径无测试覆盖
    - **low**：边界条件测试缺失、测试命名不规范

    ## 完成标志

    - 所有变更文件已审查完毕（涵盖错误处理、性能和测试三大维度）
    - 返回的 JSON 数组包含所有发现的问题
    - 如果没有发现问题，返回空数组 `[]`
