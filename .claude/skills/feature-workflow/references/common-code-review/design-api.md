# design-api — 设计一致性与 API 合规审查

Subagent：
  description: "Code Review：通用-设计与API一致性-<feature-name>"
  prompt: |
    你负责审查 <feature-name> 在 <platform> 端的实现是否与 design.md 中的架构设计和 API 定义保持一致。

    ## 背景

    特性名称：<feature-name>
    特性目录：docs/specs/<YYYY-MM-dd>-<name>/
    目标平台：<platform>

    ## 准备

    1. 通过 Skill 工具加载 `feature-workflow` skill，获取 code review 规范
    2. 读取共享设计文档 `docs/specs/<YYYY-MM-dd>-<name>/design.md`，提取其中的架构设计描述和所有 API 定义（端点、方法、参数、响应结构）
    3. 使用 `git diff main --name-only` 获取变更文件列表，仅关注 `<platform>/` 目录下的文件
    4. 逐一读取每个变更文件的内容

    ## 非首轮验证（⚠️ 仅非首轮时执行）

    检查 `docs/specs/<YYYY-MM-dd>-<name>/code-<platform>-review.md` 是否已存在。

    如果存在（第 N 轮，N > 1）：
    说明这是重新审查，**在开始新的审查之前，必须先验证上一轮属于当前审查维度的问题是否真正被修复**。

    1. 读取 code-<platform>-review.md 中**属于当前审查维度**且标记为 `✅ 已修复` 的问题
    2. 逐一读取对应文件的当前内容，验证问题是否真正被修复：
       - 问题描述的缺陷是否已不存在于当前代码中？
       - 修复后的代码是否符合修复建议？
       - 修复是否完整（而非只解决了一半）？
    3. 验证结果追加到返回的 JSON 数组中：
       - 标记已修复但实际未改 → `severity: "high"`，title 中以「验证-未修复」标注
       - 标记已修复但修复不完整 → `severity: "medium"`，title 中以「验证-修复不完整」标注

    如果不存在（首轮审查），跳过此步骤。


    ## API 定义提取方法

    从 design.md 中提取 API 定义时，关注以下模式：
    - 标记为 API/接口/端点的章节
    - 包含 HTTP 方法 + 路径的模式（如 `GET /api/users`、`POST /api/users`）
    - 表格形式的 API 清单
    - 请求/响应示例代码块
    - 路径参数和查询参数描述

    ## 审查维度

    你**只审查以下两大维度**，不涉及其他方面（代码风格、性能等由其他 subagent 负责）：

    ---

    ### 第一部分：设计一致性

    #### 1. 组件/模块拆分是否与设计一致

    - 设计文档中定义的模块/组件/类是否都在代码中有对应实现？
    - 模块的职责划分是否与设计一致？（是否有多余的模块、或者模块承担了不属于它的职责）
    - 模块之间的依赖关系是否符合设计中的描述？
    - 对于每个设计中的模块，检查是否存在对应文件/目录

    #### 2. 数据流是否符合设计中的描述

    - 数据如何从入口流向各个模块，是否符合设计文档中的描述？
    - 状态管理、数据传递方式是否与设计一致？
    - 数据转换/映射逻辑的位置是否与设计一致？
    - 如果设计中有数据流图或文字描述，逐一核对实现

    #### 3. 接口调用是否与设计中的 API 定义一致

    - 实现中调用的 API 端点是否与 design.md 中定义的一致？
    - 请求方法、路径、参数是否匹配？
    - 响应数据的使用是否与设计中的数据结构一致？
    - 注意：这里只检查"是否一致"，不检查 API 调用的正确性或错误处理（由 quality subagent 负责）

    #### 4. 是否有偏离设计的实现

    - 是否存在设计中没有提到的额外实现？（额外的组件、服务、工具等）
    - 是否存在设计中有但实现中缺失的部分？
    - 偏离设计的部分是否有合理的理由？（需要在 review 中特别标注）
    - 任何偏离都应标记为至少 medium 严重度

    ---

    ### 第二部分：API 合规性

    #### 5. API 路径是否与 design.md 定义一致

    - 代码中使用的 API 路径是否与 design.md 中定义的完全匹配？
    - 路径参数命名是否一致？（如 `:id` vs `:userId`）
    - 查询参数名是否一致？
    - API 版本前缀是否一致？（如 `/v1/` vs `/api/`）
    - 是否存在 design.md 中未定义的 API 调用？

    #### 6. HTTP 方法是否正确

    - GET 请求是否用于读取操作？（而非修改数据）
    - POST 请求是否用于创建资源？
    - PUT/PATCH 是否用于更新资源？
    - DELETE 是否用于删除资源？
    - 每个 API 调用使用的 HTTP 方法是否与 design.md 中指定的一致？

    #### 7. 请求参数格式是否与设计一致

    - 请求体的字段名、类型是否与 design.md 一致？
    - 必填参数是否都传递了？
    - 可选参数是否正确处理了默认值？
    - 参数类型是否匹配？（字符串、数字、布尔、数组、对象）
    - 嵌套对象的字段结构是否与设计一致？
    - 文件上传的 Content-Type 和 multipart 格式是否正确？

    #### 8. 响应处理是否与设计一致

    - 是否按照设计中的响应结构来解析数据？
    - 响应字段名是否与设计一致？
    - 响应数据的类型转换是否正确？
    - 分页响应结构（如 `items`、`total`、`page`、`pageSize`）是否与设计一致？
    - 是否有遗漏处理的响应字段？

    #### 9. 错误码处理是否完整

    - 是否处理了 design.md 中定义的所有业务错误码？
    - 每个错误码是否有对应的用户提示或处理逻辑？
    - 通用 HTTP 错误（401、403、404、500 等）是否有处理？
    - 是否有未在 design.md 中定义的错误码被使用？

    ## 审查方法

    对每个变更文件，逐文件对照设计文档：

    **设计一致性检查：**
    1. 理解该文件在设计中的角色
    2. 检查该文件是否实现了设计赋予它的职责
    3. 记录任何不一致之处

    **API 合规性检查：**
    4. 搜索所有 API 调用点（HTTP 请求、fetch、axios、Retrofit、URLSession 等平台特有方式）
    5. 对每个 API 调用，在 design.md 中找到对应定义
    6. 逐项比对：路径、方法、参数、响应结构、错误码
    7. 如果在 design.md 中找不到对应定义，标记为"未定义的 API"

    ## 输出格式

    返回结构化 JSON 数组，每个问题一个对象：

    ```json
    [
      {
        "file": "<platform>/path/to/file.ext",
        "line": <line_number_or_null>,
        "severity": "high" | "medium" | "low",
        "title": "问题简要标题（标注属于「设计一致性」还是「API合规性」）",
        "description": "详细描述什么与设计不一致",
        "suggestion": "建议如何修改以与设计保持一致"
      }
    ]
    ```

    ## 严重度判定标准

    **设计一致性：**
    - **high**：关键模块缺失、核心数据流方向错误、API 端点完全不对
    - **medium**：模块职责偏差、数据传递方式不同但可工作、接口参数不完全匹配
    - **low**：额外的辅助模块（功能合理）、命名与设计略有不同、文件组织结构偏差

    **API 合规性：**
    - **high**：HTTP 方法错误、API 路径与设计完全不同、使用了设计之外的 API（可能影响后端）
    - **medium**：请求参数名/类型不一致、响应字段解析不匹配、缺少必填参数
    - **low**：参数顺序不同（功能等价）、响应处理遗漏了非关键字段、错误码未完整覆盖

    ## 完成标志

    - 所有变更文件已对照设计文档审查完毕（涵盖设计一致性和 API 合规性两大维度）
    - 返回的 JSON 数组包含所有发现的不一致问题
    - 如果没有发现问题，返回空数组 `[]`
