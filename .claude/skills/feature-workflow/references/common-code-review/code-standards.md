# code-standards — 硬编码与代码风格检查

Subagent：
  description: "Code Review：通用-代码规范-<feature-name>"
  prompt: |
    你负责审查 <feature-name> 在 <platform> 端的代码中是否存在硬编码常量，以及代码风格是否符合规范。

    ## 背景

    特性名称：<feature-name>
    特性目录：docs/specs/<YYYY-MM-dd>-<name>/
    目标平台：<platform>
    项目根目录约束：禁止硬编码常量（URL、token、环境地址等），见根目录 CLAUDE.md 开发约束。

    ## 准备

    1. 通过 Skill 工具加载 `feature-workflow` skill，获取 code review 规范
    2. 读取 `<platform>/CLAUDE.md` 了解该端的配置管理规范和代码风格要求（如存在）
    3. 使用 `git diff main --name-only` 获取变更文件列表，仅关注 `<platform>/` 目录下的文件
    4. 逐一读取每个变更文件的内容

    ## 非首轮验证（⚠️ 仅非首轮时执行）

    检查 `docs/specs/<YYYY-MM-dd>-<name>/code-<platform>-review.md` 是否已存在。

    如果存在（第 N 轮，N > 1）：
    说明这是重新审查，**在开始新的审查之前，必须先验证上一轮属于当前审查维度的问题是否真正被修复**。

    1. 读取 code-<platform>-review.md 中**属于当前审查维度**且标记为 `✅ 已修复` 的问题
    2. 逐一读取对应文件的当前内容，验证问题是否真正被修复：
       - 问题描述的缺陷是否已不存在于当前代码中？
       - 修复后的代码是否符合修复建议？
       - 修复是否完整（而非只解决了一半）？
    3. 验证结果追加到返回的 JSON 数组中：
       - 标记已修复但实际未改 → `severity: "high"`，title 中以「验证-未修复」标注
       - 标记已修复但修复不完整 → `severity: "medium"`，title 中以「验证-修复不完整」标注

    如果不存在（首轮审查），跳过此步骤。


    ## 审查维度

    你**只审查以下两大维度**，不涉及其他方面：

    ---

    ### 第一部分：硬编码检查

    #### 1. URL、API 地址硬编码

    - 检查代码中是否直接写入了完整的 URL 字符串（如 `https://api.example.com/v1/users`）
    - 检查是否通过字符串拼接构造 API 路径时使用了硬编码的 base URL
    - base URL、API 版本路径应通过配置/环境变量注入
    - 例外：相对路径（如 `/api/users`）可接受，但 base URL 部分不能硬编码

    #### 2. Token、密钥硬编码

    - 检查代码中是否出现了 API key、access token、secret key 等敏感凭证
    - 检查常见的变量名模式：`token`、`secret`、`key`、`password`、`apiKey`、`accessKey` 等
    - 这些值应来自环境变量、配置文件（不提交到 git）或密钥管理服务
    - 特别注意：即使在注释中也不应出现真实的密钥值

    #### 3. 环境相关常量硬编码

    - 检查是否硬编码了环境判断（如 `if (env === 'production')`，其中 `'production'` 是硬编码字符串）
    - 检查是否硬编码了环境相关的开关值
    - 环境标识应通过统一的配置机制获取

    #### 4. 配置值硬编码

    - 检查超时时间、重试次数、分页大小、缓存过期时间等是否直接写死在代码中
    - 检查业务常量（如最大上传大小、费率、阈值等）是否硬编码
    - 这些值应通过配置文件统一管理，便于后续调整
    - 例外：纯技术常量如数组初始容量、循环计数器的边界值不属于此类

    ---

    ### 第二部分：代码风格

    #### 5. 命名规范

    - **变量**：命名是否清晰表达意图？是否避免单字母变量名（循环变量 `i`、`j`、`k` 除外）？
    - **函数/方法**：是否以动词开头？是否准确描述了函数的功能？
    - **类/组件**：是否使用名词？是否符合该平台命名惯例（如 React 组件用 PascalCase）？
    - **文件**：文件名是否与其中主要导出的类/组件/模块名一致？
    - **常量**：是否使用全大写下划线风格（如 `MAX_RETRY_COUNT`）？
    - 是否使用了平台或项目禁止的命名方式？（查阅 `<platform>/CLAUDE.md`）

    #### 6. 缩进和格式一致性

    - 同一文件内缩进风格是否一致（空格数、tab vs space）？
    - 花括号风格是否一致？
    - 空行使用是否合理（逻辑分组之间有空行，无连续多空行）？
    - import 语句是否有序分组？（第三方库、内部模块、相对路径）
    - 行长度是否合理（不超过 120 字符，如有平台规范则以平台规范为准）？

    #### 7. 注释是否清晰完整

    - 公共 API/导出的函数是否有注释说明用途、参数、返回值？
    - 复杂的业务逻辑是否有解释性注释？
    - 注释是否与代码同步？（是否存在过时注释、错误注释）
    - 是否有多余的注释掉的代码块？
    - 注释是否使用该平台推荐的语言？（通常为英文或与项目一致）

    #### 8. 是否符合 `<platform>/CLAUDE.md` 中的代码风格要求

    - 逐条检查 `<platform>/CLAUDE.md` 中列出的代码风格要求
    - 如果没有定义风格规范，则跳过此检查项
    - 如果 `<platform>/CLAUDE.md` 不存在，标注为"无平台规范可参照"

    #### 9. 是否有过度嵌套或过长函数

    - 函数体是否过长？（超过 50 行应标记为 medium，超过 100 行标记为 high）
    - 嵌套深度是否超过 4 层？（if/for/while/try 嵌套）
    - 单个函数是否承担了过多职责？（检查函数名是否能用 "and" 拆分）
    - 是否有可提取为独立函数的大段重复代码？

    ## 审查方法

    对每个变更文件：

    **硬编码检查：**
    1. 搜索 URL 模式：`https?://`、`localhost`、IP 地址模式
    2. 搜索密钥模式：`token`、`secret`、`key`、`password`、`apiKey`、`accessKey`
    3. 搜索环境字符串：`'production'`、`'development'`、`'staging'`、`'dev'`、`'prod'`
    4. 检查魔法数字：孤立的数字字面量，尝试判断其是否为业务配置值
    5. 与 `<platform>/CLAUDE.md` 中的配置管理规范交叉验证

    **代码风格检查：**
    6. 先整体扫一遍代码结构（import 区、函数分布、注释密度）
    7. 检查命名：逐个变量/函数/类名判断是否清晰
    8. 检查格式：缩进、花括号、空行
    9. 检查注释：公共接口是否有注释，注释与代码是否匹配
    10. 检查复杂度：函数长度、嵌套深度
    11. 与 `<platform>/CLAUDE.md` 对照检查

    ## 输出格式

    返回结构化 JSON 数组，每个问题一个对象：

    ```json
    [
      {
        "file": "<platform>/path/to/file.ext",
        "line": <line_number_or_null>,
        "severity": "high" | "medium" | "low",
        "title": "问题简要标题（标注属于「硬编码」还是「代码风格」）",
        "description": "详细描述问题",
        "suggestion": "建议如何修改以符合规范"
      }
    ]
    ```

    ## 严重度判定标准

    **硬编码：**
    - **high**：Token/密钥/密码硬编码在代码中（安全风险）
    - **medium**：API 地址硬编码、环境判断字符串硬编码（可维护性风险）
    - **low**：业务配置值硬编码（如超时时间、分页大小），不影响安全但降低可维护性

    **代码风格：**
    - **high**：函数超过 100 行、嵌套深度超过 5 层、命名误导性严重、注释掉的代码块过多
    - **medium**：函数 50-100 行、命名不够清晰、格式不一致、公共接口缺注释、嵌套 4-5 层
    - **low**：命名可改进但不影响理解、多余空行、import 未排序、注释措辞可优化

    ## 完成标志

    - 所有变更文件已审查完毕（涵盖硬编码检查和代码风格两大维度）
    - 返回的 JSON 数组包含所有发现的问题
    - 如果没有发现问题，返回空数组 `[]`
