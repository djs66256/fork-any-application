## 发现的问题

### 问题 1：将 mall 容器能力表述成了可直接复用的通用基础设施

- **严重程度**：🔴 高
- **维度**：一致性 / 可行性
- **描述**：初版 spec 将 mall H5 容器、bridge、host sync 写成了接近“现成通用能力”的表述，但当前仓库中的实现仍明显是 mall-specific。继续保持原说法会误导后续 design/coding 低估 earn 侧新增容器、配置与消息协议的工作量。
- **修复状态**：✅ 已修复
- **修复说明**：已在术语表、涉及平台、现有功能影响与依赖章节中明确：earn 只能复用 mall 的设计模式与分层经验，仍需新增 earn 自己的 route、配置、bridge 与 host sync，不再把现有 mall 实现写成通用能力。

### 问题 2：将登录承接误写为现成统一 H5 登录链路

- **严重程度**：🔴 高
- **维度**：一致性 / 平台覆盖
- **描述**：初版 spec 使用了“直接复用现有统一登录承接”的表述，但当前代码里真正现成的是 Native 登录能力与 mall 专属 H5 登录承接样板，不存在可直接给 earn 复用的通用 H5→登录适配层。
- **修复状态**：✅ 已修复
- **修复说明**：已改写成功指标、范围定义、US-03 流程、现有功能影响与依赖表，明确：底层复用的是现有 Native 登录能力；earn 仍需新增自己的 `requestLogin / syncAuthState / restoreContext` 语义、bridge 协议、路由参数与宿主返回处理。

### 问题 3：将播放器链路误写为已支持 earn 任务上下文与完成语义

- **严重程度**：🔴 高
- **维度**：可行性 / 完整性
- **描述**：初版 spec 默认把 `taskId/source=earn/returnTarget=/earn`、返回赚钱页以及任务完成回调写成近似现有能力，但 Android 当前只有 `play/{videoId}`，iOS 当前只有 `AppRoute.player(videoId:)`，均未承载 earn 任务上下文，也没有现成的 earn 任务完成回调语义。
- **修复状态**：✅ 已修复
- **修复说明**：已在术语表、US-04 流程、待澄清问题与参考代码章节中明确：earn 任务上下文与返回语义属于本期新增能力；首版完成条件默认采用 earn 独立回调，不依赖现有 player `progress / stop` contract 即可先打通最小闭环。

### 问题 4：低估了 Backend / Web / iOS / Android 的基础模块缺口

- **严重程度**：🟡 中
- **维度**：完整性 / 可行性 / 术语与范围
- **描述**：初版 spec 对实现范围的描述偏“补两个 API + 一个页面”，未把各端缺失的配置、schema、service、repository、registry、状态管理、bridge、容器 ViewModel / View 等基础模块写完整，容易导致后续方案设计遗漏骨架工作。
- **修复状态**：✅ 已修复
- **修复说明**：已在涉及平台、US-01/US-02 前置条件、依赖表与参考代码章节中补充各端缺失项，明确 Android / iOS / Web / Backend 都需要从配置与骨架层开始补齐最小实现。

### 问题 5：浏览器模式与 Native 模式边界不清晰

- **严重程度**：🟡 中
- **维度**：完整性
- **描述**：初版 spec 虽要求浏览器可访问 `/earn`，但没有明确浏览器模式是否需要真实打开 Native 登录或播放器，导致开发与验收边界不清。
- **修复状态**：✅ 已修复
- **修复说明**：已新增“浏览器模式”术语，并在成功指标、范围定义、US-03 异常说明中明确：浏览器模式仅覆盖 H5 UI、接口、空态/错误态与按钮降级反馈，不要求真实调用 Native bridge、登录或播放器。
