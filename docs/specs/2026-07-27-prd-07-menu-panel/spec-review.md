## 发现的问题

### 问题 1：菜单面板的承载层级与当前首页壳结构未对齐

- **严重程度**：🔴 高
- **维度**：可行性 / 平台覆盖
- **描述**：`spec.md` 目前只描述了“首页顶部新增汉堡按钮 + 左侧抽屉覆盖首页与底部 Tab”，但没有说明菜单面板状态应该挂在哪一层。当前 Android 的底部栏在 `android/app/src/main/java/com/djs66256/short_drama/navigation/NavGraph.kt` 的 `Scaffold` 中，位于 `HomeScreen` 外层；iOS 的 Tab 容器在 `ios/ShortDrama/Sources/App/AppShellView.swift`，`HomeView` 只是 `TabView` 内的一个页面。如果把抽屉状态只放在 `HomeScreen` / `HomeView`，很难满足“底部 Tab 保留为背景但不可交互”的要求，也会让蒙层覆盖范围、返回关闭、占位页跳转后的状态恢复都变得不明确。建议在 spec 中明确：菜单面板由应用壳层承载（Android 至少提升到 `NavGraph` 层，iOS 至少提升到 `AppShellView` / `TabNavigationHostView` 可控层），或者明确放宽为“仅覆盖首页内容区，不覆盖底部 Tab”。
- **修复状态**：✅ 已修复
- **修复说明**：已在 `spec.md` 中明确菜单面板由应用壳层承载，Android 提升到 `NavGraph` / 外层 `Scaffold` 可控层，iOS 提升到 `AppShellView` / `TabNavigationHostView` 可控层，并定义打开后覆盖首页内容区与底部 Tab 的不可交互层。

### 问题 2：最近在看的会话来源描述与当前 playback session 能力不一致

- **严重程度**：🟡 中
- **维度**：一致性 / 完整性
- **描述**：`spec.md` 将最近在看请求描述为“复用当前播放器已使用的 `X-Playback-Session-Id`”，并把缺失 header 视为一个常规异常分支；但当前代码里 Android 的 `DataStorePlaybackSessionStore`（`android/app/src/main/java/com/djs66256/short_drama/core/storage/PlaybackSessionStore.kt`）和 iOS 的 `KeychainPlaybackSessionStore`（`ios/ShortDrama/Sources/Core/Storage/PlaybackSessionStore.swift`）都支持在未进入播放器时直接生成并复用会话 ID。也就是说，新用户首次从首页打开菜单时，不应依赖“当前播放器已存在的 header”。建议在 spec 中改为“菜单面板与播放器共用同一套 playback session store，打开面板前先 get-or-create session id，再请求最近在看接口”，并把“缺失 header”降级为实现异常而非正常用户路径。
- **修复状态**：✅ 已修复
- **修复说明**：已在 `spec.md` 中改写为菜单面板与播放器共用 playback session store，客户端在请求最近在看前先执行 get-or-create session id，并将缺失 header 降级为实现异常而非常规用户路径。

### 问题 3：最近在看接口路径与当前 Backend 能力分组不一致

- **严重程度**：🟡 中
- **维度**：一致性 / 术语与范围
- **描述**：`spec.md` 新增的接口路径是 `GET /api/user/recently-viewed`，但当前 Backend 里与播放历史相关的能力都归在 `/api/player/*`（`backend/src/app/api/player/progress/route.ts`、`start/route.ts`、`stop/route.ts`），仓储和 service 也都是按 playback history / player 能力建模，仓库内没有既有的 `/api/user` 命名空间，而且该接口首版也不依赖账号体系。继续使用 `/api/user/recently-viewed` 会让“匿名播放会话历史”被误表述成“用户中心资源”。建议在 spec 中要么将接口调整为与现有 player/history 域一致的命名，要么明确解释为什么要现在引入新的 `/api/user` 资源分组，以及它与未来登录态的衔接关系。
- **修复状态**：✅ 已修复
- **修复说明**：已将最近在看接口统一收敛为 `GET /api/player/recently-viewed`，并在范围、流程、数据概览与兼容性章节中明确其归属 player / playback-history 领域，而非 user 领域。

### 问题 4：占位承接页的返回行为定义前后不一致

- **严重程度**：🟡 中
- **维度**：完整性
- **描述**：`spec.md` 第 5.2 节要求登录 / 消息 / 我的预约 / 我的下载点击后进入占位承接页，并说明占位页“支持返回关闭到上一层”；但边界场景又写“从占位承接页返回，回到菜单打开前的页面上下文”。这两句会导向两种完全不同的实现：一是返回后回到“菜单仍然打开”的状态，二是返回后回到“首页且菜单关闭”的状态。两端当前都还没有这些路由，若不先定清楚，导航状态、抽屉关闭时机和验收口径都会分叉。建议在 spec 中明确：进入占位页时菜单是否自动关闭；从占位页返回时究竟落到“菜单打开态”还是“首页常态”，并在 Android / iOS 一致执行。
- **修复状态**：✅ 已修复
- **修复说明**：已统一占位承接页导航语义：所有登录 / 消息 / 预约 / 下载入口均先关闭抽屉再跳转，占位页返回后回到首页常态，菜单保持关闭，并在流程与边界章节同步说明。

### 问题 5：“我的预约”与当前已存在的预约能力边界没有说清

- **严重程度**：🟡 中
- **维度**：一致性 / 范围
- **描述**：当前项目已经存在排行页预约能力与相关数据模型（例如 `POST /api/dramas/:id/book`、`booking_count`、`is_booked`，见 `backend/src/lib/schemas.ts` 与排行相关代码 / wiki），但 `spec.md` 只说“我的预约”本期做占位承接，没有明确说明它不会读取现有预约状态、不会展示已预约短剧列表、也不会与排行页的预约结果打通。这样会导致实现和验收对“我的预约”理解不一致。建议在 spec 中补充明确边界：本 PRD 的“我的预约”仅提供静态入口与占位页，不消费现有预约数据，也不承担预约资产管理。
- **修复状态**：✅ 已修复
- **修复说明**：已在范围、信息架构与现有功能影响章节中明确“我的预约”首版仅提供静态入口与占位承接，不读取排行预约能力、不展示预约资产列表，也不承担预约管理职责。

### 问题 6：边界与错误处理覆盖仍不完整

- **严重程度**：🟡 中
- **维度**：边界与错误处理
- **描述**：当前 `spec.md` 已覆盖了部分空态、服务端错误和无效数据过滤，但仍缺少审查规范要求的若干关键链路：1）最近在看请求的断网、超时、DNS 失败、502/503 等客户端可见异常；2）菜单面板打开时最近在看请求正在进行、用户快速开关面板或重复点击重试的并发行为；3）占位承接入口在重复点击、路由创建失败或页面尚未 ready 时的兜底行为；4）错误提示文案规范里没有明确“不展示原始错误码 / 技术细节”。建议补齐错误类型 → 触发条件 → 系统行为 → 用户感知的完整链路，并区分“局部错误态”“Toast/HUD”“静默忽略”的适用场景。
- **修复状态**：✅ 已修复
- **修复说明**：已在菜单面板、占位承接页与最近在看章节补充断网、超时、DNS 失败、502/503、重复点击、并发开关、路由未 ready、错误文案不暴露技术细节等完整错误矩阵。

### 问题 7：待澄清问题仍保留了可直接默认的非阻塞项

- **严重程度**：🟢 低
- **维度**：完整性 / 术语与范围
- **描述**：第 10 节的 `Q-01 ~ Q-03` 都标记为“不阻塞”，但至少其中两项已经可以按现状默认收敛：`Q-02` 可直接默认首版只展示“已看到第 N 集”，因为当前接口设计只聚合 `episode_number`；`Q-03` 可直接默认静态系统文案，因为当前代码和架构里都没有消息运营配置能力；`Q-01` 又属于未来登录态 UI 演进，不影响本期。继续把这些问题留在“待澄清问题”中，会稀释真正需要 human review 的焦点。建议在 spec 中把可默认项直接收敛为默认决策，未来态问题则移到“后续演进说明”或对应后续 PRD。
- **修复状态**：✅ 已修复
- **修复说明**：已删除可默认收敛的非阻塞待澄清项，并改为“当前无阻塞推进的待澄清问题”，同时把最近在看展示文案、消息预览静态文案和登录头部未来演进收敛为默认决策。
