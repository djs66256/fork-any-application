# 决策记录：页面 UI 对齐整改拆分为多个 PRD

- **日期**：2026-07-30
- **触发**：用户反馈（“这一个需求有点大，你需要将其拆分为多个需求”）
- **状态**：已确认

---

## 背景

此前页面 UI 对齐整改被作为一个统一的大需求看待，覆盖首页、播放器、搜索发现、菜单与个人相关页、剧场、商城、赚钱中心以及宿主联调。基于既有 product-manager 体系，这种粒度过大：

- `progress.md` 以 PRD 为最小跟踪单位
- `backlog.md`、`sprint.md`、`roadmap.md` 都围绕单个功能 PRD 管理
- 统一大 PRD 会同时跨多个页面域、多个端和多组前置依赖，不利于排期、验收和后续 feature-workflow 启动

## 分析

### 现有拆分模式

仓库当前的既有模式是：

1. **按功能/页面模块拆 PRD**，而不是把横跨多个域的大主题保留为一个总 PRD
2. **在单个 PRD 内再按用户故事和子任务拆分**，而不是把跨域内容全部塞进 subtasks
3. 当功能过大时，允许继续拆为多个 PRD 或多个迭代条目

因此，页面 UI 对齐整改更适合作为一个专题来管理，而不是继续保留为单一总 PRD。

### 共享约束

以下内容应在所有拆分 PRD 中保持一致：

- 截图基线统一来自 `docs/product_research/mobile/`
- 对齐目标优先是结构、模块顺序、信息层级和主次 CTA，对素材允许首版占位
- `mall / earn` 继续由 H5 承载，不切回独立 Native 页面
- 首页、播放器、搜索、排行、分类、剧场、评论继续以 Native 为主
- 评论登录恢复继续遵守“只恢复容器，不自动重放写操作”
- 既有 Bridge / host message / restoreContext 语义不改变
- Backend 仅补充最小展示支撑，不新增新的业务域或重写 RESTful contract

## 决策

将“页面 UI 对齐整改”拆分为以下 6 个独立 PRD：

1. `PRD-16 首页 Feed UI 对齐`
2. `PRD-17 播放器与评论 UI 对齐`
3. `PRD-18 搜索发现体系 UI 对齐`
4. `PRD-19 菜单与个人相关页 UI 对齐`
5. `PRD-20 剧场频道 UI 对齐`
6. `PRD-21 商业化页面与宿主 UI 对齐`

不再保留一个父级总 PRD 作为 `progress.md` 中的独立跟踪条目。

## 推进顺序

1. 第一批：`PRD-16`、`PRD-17`
2. 第二批：`PRD-18`、`PRD-20`
3. 第三批：`PRD-19`、`PRD-21`
