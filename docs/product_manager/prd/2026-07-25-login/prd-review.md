## 🔴 阻塞问题

### B-01：Auth 中间件仍为骨架，缺少升级计划 ✅ 已修正

- **位置**：`subtasks.md` ST-01
- **问题**：当前 `backend/src/middleware/auth.ts` 为骨架实现——仅校验 `Bearer` 格式后即放行，不执行真实 JWT 验证。登录功能上线后，所有标记为"需要登录"的 API（评论、预约等）仍会接受任意字符串作为 token，无法真正保护接口。
- **修正方案**：
  1. 在 ST-01 中新增子任务：将 `auth.ts` 从骨架升级为真实 Supabase JWT 校验（`supabase.auth.getUser(jwt)`）
  2. 或新增独立的 `ST-01b：Auth 中间件升级`，工时 +0.5 人日

### B-02：缺少登出 API 端点 ✅ 已修正

- **位置**：`subtasks.md` ST-01
- **问题**：US-04 要求退出登录并清除 Token，但 ST-01 仅列出 `send-code`、`verify-code`、`me` 三个端点，缺少登出/会话清除端点。
- **修正方案**：ST-01 中补充 `POST /api/auth/logout` 端点，调用 `supabase.auth.signOut()` 使当前 session 失效并清除客户端 Token。

### B-03：子任务中的"抖音登录占位"与 PRD 范围定义矛盾 ✅ 已修正

- **位置**：`subtasks.md` ST-02 描述
- **问题**：ST-02（iOS）描述中包含「抖音登录占位」，但 PRD 第 1.4 节明确将「第三方登录（抖音/微信/Apple）」列为范围外。两者矛盾。
- **修正方案**：从 ST-02 和 ST-03 描述中移除第三方登录占位相关描述，或同步更新 PRD 第 1.4 节说明"保留占位入口但不实现功能"。推荐前者以保持范围一致。

### B-04：短信服务商未选定，阻塞开发 ✅ 已修正

- **位置**：PRD 第 6 节 Q-02
- **问题**：Q-02 标注为"否（不阻塞）"，但 Supabase Auth 的手机号验证码登录**必须**配置 SMS provider（如 Twilio、Vonage、MessageBird），否则无法发送验证码。这不是 spec 阶段才需确认的问题，而是开发启动即需解决。
- **修正方案**：将 Q-02 的阻塞状态改为"是"，并在开发启动前完成 SMS provider 选型与配置。同时在 ST-01 中补充"SMS provider 配置"为子任务步骤。

### B-05：API 设计未说明前端直接调用 Supabase Auth 还是通过 Backend 代理 ✅ 已修正

- **位置**：PRD 第 4.1 节 + `subtasks.md` ST-01
- **问题**：Supabase Auth 的 SDK 支持客户端直接调用（`supabase.auth.signInWithOtp` / `verifyOtp`），不必须通过 Backend 代理。PRD 中设计了 `POST /api/auth/send-code` 和 `POST /api/auth/verify-code` 作为 Backend 端点，但未说明为何选择这种方式。如果移动端直接调用 Supabase SDK，则 Backend 根本不需要这两个端点，只需升级 auth middleware 即可。这直接影响了 ST-01 的工时估算和工作内容。
- **修正方案**：在 PRD 中增加设计决策说明——选择 Backend 代理还是客户端直连 Supabase Auth。如选择 Backend 代理，需说明理由（如：统一限流、隐藏 Supabase Key）。如选择客户端直连，则 ST-01 只需覆盖 auth middleware 升级 + `/api/auth/me` + `/api/auth/logout`，工时可缩减。

## 🟡 建议

### S-01：缺少错误场景定义 ✅ 已修正

- **位置**：PRD 第 4.1 节
- **问题**：核心流程仅覆盖成功路径，未定义异常场景的 UI 与行为：
  - 验证码输入错误 → 提示"验证码错误，请重新输入"，允许重试 N 次
  - 验证码过期 → 提示"验证码已过期，请重新获取"
  - 发送过于频繁 → 按钮倒计时 + 提示"请 N 秒后重试"
  - 手机号已被注册 → 直接进入登录流程（因为本身就是注册+登录合一）
  - 网络异常 → Toast 提示"网络异常，请稍后重试"
- **修正方案**：在第 4 节中新增 4.x「异常场景」表格，列出各错误码及对应 UI 行为。

### S-02：Token 刷新策略未定义 ✅ 已修正

- **位置**：PRD 第 1.4 节 / US-03
- **问题**：US-03 要求"自动恢复登录态"，PRD 范围中提到"Token 存储+自动刷新"，但未说明刷新策略：何时刷新（过期前 N 分钟？）、刷新失败行为（是否退登？）、是否使用 Supabase 的 `onAuthStateChange` 自动管理。
- **修正方案**：在第 4 节补充 Token 管理策略一节，明确：使用 `supabase.auth.onAuthStateChange` 自动监听 session 变化；session 过期时 Supabase SDK 自动尝试 refresh；refresh 失败后清除本地状态回匿名态。

### S-03：用户协议内容与链接缺失 ✅ 已修正

- **位置**：PRD US-02 / 第 4.1 节
- **问题**：US-02 要求用户勾选"用户协议+隐私政策"复选框，但 PRD 未定义：
  - 协议文本内容从何而来（静态 HTML？后端配置？）
  - 点击协议链接后打开什么页面（WebView？外部浏览器？）
  - 如果不勾选，登录按钮是完全不可点击还是点击后 Toast 提示
- **修正方案**：在第 4.1 节 UI/交互要点中补充：协议链接点击后在 App 内 WebView 打开；先上静态文案页面，远期可配置；未勾选时按钮置灰不可点击（参考竞品行为）。

### S-04：退出登录入口位置未与 PRD-07 对齐 ✅ 已修正

- **位置**：PRD US-04
- **问题**：US-04 描述为"在菜单面板/设置中可退出登录"，但 PRD-07（菜单面板）的 UI 布局中并无退出登录入口，也未提及登录后的展示态（当前仅描述了匿名态的登录引导）。需要明确退出登录入口究竟在菜单面板的哪个位置，以及由哪个 PRD 负责实现。
- **修正方案**：与 PRD-07 协调——可以在菜单面板底部新增"设置"入口行，其中包含退出登录；或在本 PRD 中明确退出登录入口放在菜单面板底部，由本 PRD 的 iOS/Android 子任务实现。

### S-05：US-05（登录拦截）优先级建议提升 ✅ 已修正

- **位置**：PRD 第 3 节 US-05
- **问题**：US-05"操作拦截跳转登录"目前优先级为 P1，但如果没有这个拦截能力，登录功能的价值非常有限——用户不会主动去登录，需要有"执行需登录操作 → 被拦截 → 引导登录"的闭环。建议评估是否提升至 P0，至少保证 1-2 个场景的拦截可用。
- **修正方案**：将 US-05 提升至 P0，或至少在 P0 阶段实现评论拦截（因为评论是 Sprint 4 同期的 P1 功能，登录是它的前置依赖）。

### S-06：手机号校验规则未定义 ✅ 已修正

- **位置**：PRD 第 4.1 节流程图
- **问题**：流程图中包含"手机号格式正确？"判断节点，但未定义校验规则：仅校验长度（11 位中国手机号）？还是校验号段前缀（13x/15x/18x 等）？服务端是否重复校验？
- **修正方案**：在第 4.1 节补充：前端校验 11 位数字、以 1 开头；服务端使用 Supabase Auth 内置 format 校验；区号选择器范围（+86 默认，是否支持其他国家区号）。

### S-07：缺少首次安装引导考虑 ✅ 已修正

- **位置**：PRD 全文
- **问题**：PRD 未提及首次安装/冷启动场景下的用户引导。竞品（红果）在首次进入时可能展示引导页或直接进入首页。是否需要首次安装即弹登录页？还是保持竞品策略——先让用户浏览内容，在触发需要身份的操作时才引导登录？
- **修正方案**：在第 1.4 节范围定义中补充说明：首次安装不强制登录，用户可匿名浏览；仅在触发 US-05 拦截场景或主动点击登录入口时才引导。

### S-08：子任务中 Android ST-03 描述过简 ✅ 已修正

- **位置**：`subtasks.md` ST-03
- **问题**：ST-03（Android 登录页 UI + Token 管理）仅有一行描述，无具体内容拆解。而 ST-02（iOS）有完整描述"登录页（手机号+验证码+协议勾选+抖音登录占位）、Token 存储（Keychain）、自动登录恢复"。
- **修正方案**：ST-03 补充与 ST-02 对等的描述：登录页（手机号+验证码+协议勾选）、Token 存储（EncryptedSharedPreferences / DataStore）、自动登录恢复。

### S-09：Backend ST-01 工时评估偏紧 ✅ 已修正

- **位置**：`subtasks.md` ST-01
- **问题**：ST-01 工时 2 人日，但实际工作范围应包括：Supabase Auth provider 配置（Phone）、SMS provider 配置、auth middleware 升级（如按 B-01 修正）、3 个 API 端点（可能增至 4 个）、单元测试。在当前工作量下 2 人日较紧。
- **修正方案**：按 B-01/B-02 修正后，建议工时调整为 2.5-3 人日。如按 B-05 选择客户端直连方案，则可保持 1.5-2 人日。
