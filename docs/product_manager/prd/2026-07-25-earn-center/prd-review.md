## 🔴 阻塞问题（全部已修正 ✅）

### B-01：ST-03 Android 端描述缺失 ✅ 已修正

- **位置**：`subtasks.md` ST-03 行
- **问题**：ST-03（Android 赚钱中心页 UI）仅有工时和优先级，完全没有功能描述。与 ST-02（iOS）对比，iOS 端有明确的「收益头图、新手任务卡片、连续看剧福利网格、现金任务列表」描述，Android 端却为空。
- **影响**：开发者无法从子任务文档理解 Android 端需要实现什么。
- **修正方案**：
  1. 补全 ST-03 描述，内容与 ST-02 对齐：`收益头图、新手任务卡片、连续看剧福利网格、现金任务列表`
  2. 或如果两端的 UI 描述完全一致，在 ST-03 中注明「同 ST-02，Android 端实现」，避免复制粘贴造成的维护不一致

### B-02：核心流程缺少 mermaid 流程图 ✅ 已修正

- **位置**：`prd.md` 第 4 节
- **问题**：核心流程仅一行文字描述：「用户进入赚钱 Tab → 浏览奖励/任务 → 点击「立即领取」→ 跳转播放页 → 观看短剧完成任务」。缺少 mermaid 流程图，无法清晰展示分支逻辑（如点击不同任务类型、返回路径、登录/未登录分支）。
- **影响**：开发者无法直观理解完整交互流程，容易遗漏边缘路径。
- **修正方案**：
  1. 补充 mermaid flowchart，至少覆盖以下路径：
     - 未登录用户 → 看到收益头图 + 登录入口 → 登录 → 刷新收益
     - 已登录用户 → 浏览任务 → 点击「立即领取」→ 跳转播放页 → 观看 → 完成任务
     - 播放页返回 → 回到赚钱 Tab，导航高亮保持
  2. 参考竞品文档 `earn-center.md` 中已有的三条状态路径（浏览态、播放承接态、返回后赚钱态）来构建流程图

### B-03：「虚拟货币」概念未定义 ✅ 已修正

- **位置**：`prd.md` 第 1.3 节范围定义、US-01 验收标准
- **问题**：「虚拟货币」是赚钱中心的核心展示数据，但 PRD 中从未定义它是什么——是「金币」「积分」「现金（分）」还是纯占位数字？这直接影响：
  - API 返回字段命名（`virtual_coins`？`points`？`balance`？）
  - UI 展示（是否带「¥」符号？数字格式？）
  - 与签到系统（PRD-10）的未来对接（签到奖励以什么单位结算？）
- **影响**：前后端开发者无法对齐数据格式，后续对接签到系统时需要返工。
- **修正方案**：
  1. 在 PRD 第 5 节（依赖）或新增一个小节中明确定义虚拟货币的概念：
     - 名称（如「金币」）
     - 展示格式（如整数、带「金币」后缀）
     - 首版为前端 mock 数据 / 后端种子数据，不做真实增减
  2. 与 PRD-10 协调统一的虚拟货币单位，确保签到奖励未来可直接汇入赚钱中心货币体系

### B-04：「奖励通过看剧完成」机制未展开 ✅ 已修正

- **位置**：`prd.md` US-02 验收标准
- **问题**：US-02 的验收标准写的是「点击『立即领取』→ 跳转播放页（奖励通过看剧完成）」，但括号内的机制完全没有展开：
  - 看多少集/多少分钟算完成任务？
  - 后端如何记录观看进度与任务进度的关联？
  - 用户如何知道自己已完成任务？
  - 完成后用户回到赚钱中心还是停留在播放页？
- **影响**：这是一条端到端的核心用户路径（US-02 是 P0），缺乏机制定义会导致 Backend API 和客户端交互逻辑无法设计。
- **修正方案**：
  1. 明确任务完成条件，例如：「在播放页观看完整一集（或连续观看 N 分钟）」即视为任务完成
  2. 补充后端记录机制：`POST /api/player/stop` 上报播放进度时，携带 `task_id` 参数，后端校验并更新任务状态
  3. 补充 UI 交互：任务完成后，播放页内展示完成提示（Toast/浮层），用户可继续观看或返回赚钱中心

### B-05：US-02 验收标准不完整，无法验证 ✅ 已修正

- **位置**：`prd.md` US-02 行
- **问题**：US-02 的验收标准「点击『立即领取』→ 跳转播放页（奖励通过看剧完成）」仅描述了触发动作，没有描述期望结果。验收标准应当是「当 X 发生，则 Y 结果出现」的格式。当前写法中，用户点击后只是跳转了，奖励是否到账、如何确认任务完成，全部缺失。
- **影响**：QA 无法编写测试用例，开发者无法判断功能是否完成。
- **修正方案**：
  1. 重写 US-02 验收标准为可验证格式，例如：
     - 「用户点击『立即领取』→ 跳转至携带任务上下文的播放页」
     - 「用户在播放页观看完指定内容后，返回赚钱中心时收益数值更新」
     - 「若用户未完成观看即退出，任务状态保留，下次可继续」

## 🟡 建议（全部已修正 ✅）

### S-01：缺少 UI/交互要点表格 ✅ 已修正

- **位置**：`prd.md` 第 4 节之后
- **问题**：竞品分析文档 `earn-center.md` 已提供了详细的 UI 布局表格（收益头图、新手任务区、连续看剧福利区、现金任务区，含组件和规格），但 PRD 中没有引用或提炼。缺少 UI 要点会让设计师和前端开发缺乏明确的布局指引。
- **修正方案**：
  1. 在 PRD 中新增一节「UI/交互要点」，引用竞品文档中的布局表格，并标注各区域的优先级（P0/P1）
  2. 至少包含：顶部收益头图（含登录入口）、新手任务区（卡片 + 按钮）、连续看剧福利区（宫格）、现金任务区（列表）

### S-02：工时 10 人日与 backlog B-006 的 14 人日不一致 ✅ 已修正

- **位置**：`subtasks.md` 工时总览 vs `backlog.md` B-006
- **问题**：backlog 中 B-006 估为 14 人日（含「提现」），PRD 明确将「真实提现」标为范围外，subtasks 总计 10 人日。但即便扣除提现的工时，仍缺少对差异的解释。Backlog 中 14 人日可能基于更完整的范围（含任务系统逻辑、提现 UI 等），PRD 缩小范围后应同步更新 backlog 或注明差异原因。
- **修正方案**：
  1. 在 subtasks.md 工时总览中增加一行备注：`backlog 原估 14 人日含提现等范围外功能，本迭代 10 人日`
  2. 同步更新 `backlog.md` 中 B-006 的工时和备注，使其与 PRD 范围一致

### S-03：任务数据模型未定义 ✅ 已修正

- **位置**：`prd.md` 整体
- **问题**：PRD 涉及 4 种任务/奖励类型（收益展示、新手任务、连续看剧福利、现金任务），但未定义任务的数据结构。例如：任务 ID、类型枚举、标题、奖励金额、完成条件、状态等字段。Backend API `GET /api/earn/overview` 需要返回任务列表，缺失数据模型定义会导致 API 设计草率。
- **修正方案**：
  1. 在 PRD 第 5 节（依赖）后增加「数据模型概要」小节，定义 Task 实体的核心字段：
     - `task_id`、`task_type`（newbie / daily_watch / cash）、`title`、`reward_amount`、`reward_unit`（虚拟货币单位）、`status`（available / in_progress / completed / claimed）、`action`（跳转目标，如播放页路由）
  2. 注意与 PRD-10 签到奖励的数据结构保持可对接

### S-04：仅一个 API 端点可能不够 ✅ 已修正

- **位置**：`subtasks.md` ST-01
- **问题**：ST-01 仅设计了 `GET /api/earn/overview` 一个端点。但 US-02 的领取流程需要：
  - 用户点击「立即领取」时是否需要 `POST /api/earn/claim` 记录领取行为？
  - 播放完成后是否需要 `POST /api/earn/complete` 标记任务完成？
  - 收益数值变更是否需要端点支持？
- **修正方案**：
  1. 补充 API 设计，至少考虑增加：
     - `POST /api/earn/tasks/{task_id}/start` — 用户开始一个任务（记录起始状态）
     - `POST /api/earn/tasks/{task_id}/complete` — 任务完成回调（由播放器 `stop` 事件触发或客户端主动上报）
  2. 如果首版仅做展示（纯 mock 数据），在 ST-01 中明确标注「首版仅提供 GET 端点，回报种子数据，不做真实任务流转」

### S-05：PRD-10 签到奖励与赚钱中心的对接路径不清晰 ✅ 已修正

- **位置**：`prd.md` 整体 + PRD-10 交叉引用
- **问题**：PRD-10（签到与消息系统）明确指出「签到奖励表现：首版为纯 UI 高亮格子（无实际金币），远期接入 PRD-14 赚钱中心」。PRD-14（本 PRD）也使用「虚拟货币」占位。两者首版都是虚拟的，但：
  - 两者使用同一个「虚拟货币」概念还是各自独立的？
  - 远期对接时，签到是直接调用赚钱中心的 API 加币，还是签到系统自己维护金币然后同步？
  - 当前没有任何跨 PRD 的协调说明
- **修正方案**：
  1. 在 PRD 的依赖表中增加一行：「签到系统 | 内部能力 | 签到奖励远期汇入虚拟货币体系 | 📅 PRD-10」
  2. 在 PRD-10 中也同步增加对 PRD-14 的依赖引用，确保双向可见

### S-06：连续看剧福利的每日网格卡片交互未说明 ✅ 已修正

### S-07：缺少现有功能影响章节 ✅ 已修正
