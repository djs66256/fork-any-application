## 逐维度详细审查

### 完整性

PRD 整体结构清晰，包含需求背景、目标用户、预期目标、范围定义、用户故事、核心流程、依赖和待澄清问题等完整章节。范围定义表写得很好，明确列出了「不做什么」和原因。

发现 3 个建议项：

- **R-03**：匿名态下点赞/收藏的本地状态在用户后续登录时如何同步到后端未定义。US-03 只描述了「匿名态本地生效、登录态调用 API」，但缺少两种状态切换时的过渡逻辑。
- **R-04**：US-04（CTA 跳转播放页）缺少独立的核心流程章节。US-01/02 和 US-03 都有详细的用户旅程 + mermaid 流程图 + UI/交互要点表 + 关键边界表，但 US-04 仅在 4.1 的 UI 表格中出现了一行。作为 P0 用户故事，跳转流程应和其他故事保持一致的信息密度。
- **R-06**：子任务 ST-05/ST-06 的工作内容中包含「头像（作者头像占位）」，但 PRD 的用户故事（第 3 节）和 UI/交互要点表（4.1）中均未提及作者头像。当前数据模型（Drama schema）没有 author 字段，backlog.md 中也没有「作者系统」相关的 PRD。该 UI 元素是否属于本 PRD 范围需要明确。

值得肯定的点：
- 每个用户故事都有明确的验收标准和优先级。
- 核心流程配有 mermaid 流程图，可读性强。
- 关键边界表覆盖了网络异常、空数据、最后一页等常见场景。
- 待澄清问题（Q-01、Q-02）已经标记了阻塞程度和首版方案，有助于推进。

### 可落地性

子任务拆分合理，6 个子任务分布在 2 个 Sprint 中，依赖关系通过 mermaid 图清晰表达。无单子任务超过 5 人日限制。工时估算说明列出了关键假设。

发现 2 个阻塞项、1 个建议项：

- **R-01**：API 响应格式不一致。PRD 4.1 和 ST-01 描述的响应格式为 `{ data: Drama[], total: number, page: number, pageSize: number }`，但现有 wiki API 文档（`wiki/api/dramas.md`）定义的格式为 `{ data: [], pagination: { page, page_size, total, total_pages } }`（嵌套分页对象、snake_case 字段名）。Backend 已有骨架实现，响应格式应以现有代码和 wiki 为准，ST-01 需要对齐。
- **R-02**：ST-02 要求 Drama 模型新增 `like_count` 和 `favorite_count` 字段，但当前 Drama schema（wiki data-models）不包含这两个字段。ST-02 的完成标准中提到「需新增 Schema 字段」，但 PRD 依赖表中将「数据模型 (Drama)」标记为「✅ 已就绪」，这与实际需要扩展 schema 的事实矛盾。Schema 扩展需要变更数据库 migration，属于 ST-02 的前置工作。
- **R-07**：ST-01 中 pageSize 最大值设为 20，但现有代码（`backend/src/app/api/dramas/route.ts`）和 wiki API 文档中 pageSize 最大值均为 100。两者不一致，实现时会产生歧义。

值得肯定的点：
- 子任务依赖图（mermaid）清晰展示了跨 Sprint 的依赖关系。
- 每个子任务都有 checkbox 格式的完成标准。
- 工时估算说明列出了 4 个关键假设，让估算有据可依。
- ST-03/ST-04 的工作内容中明确引用了各端的技术栈组件（SwiftUI `AsyncImage`、Compose Coil、`LazyVStack`/`LazyColumn`），说明子任务已经考虑了技术可行性。

### 跨端一致性

iOS 和 Android 各有对应的 Feed UI 和交互栏子任务（ST-03/ST-04、ST-05/ST-06），结构对称。两端的 UI 组件映射清晰（`HomePage` ↔ `HomeScreen`、`FeedCardView` ↔ `FeedCard`）。

发现 1 个建议项：

- **R-05**：ST-03（iOS）完成标准中包含「下拉刷新重新加载第 1 页」，但 ST-04（Android）完成标准中缺失此项。ST-04 的工作内容中明确写了「下拉刷新：`pullRefresh` modifier」，说明功能是要实现的，只是完成标准漏写了。

值得肯定的点：
- 两端使用的技术栈对应关系明确（SwiftUI ↔ Jetpack Compose、AsyncImage ↔ Coil）。
- 两端交互栏结构完全对齐（头像 + 点赞 + 收藏 + 评论 + 分享）。

### 冲突检测

backlog.md 中所有功能均为 P0/P1/P2 规划状态，progress.md 中 building 状态为 0，不存在与进行中任务的冲突。

发现 1 个建议项：

- **R-08**：backlog.md 中 B-001（首页 Feed 流）预估 15 人日，但 subtasks.md 总工时为 14 人日。虽然差异仅 1 人日，但 backlog 和 subtasks 应保持一致。

值得肯定的点：
- PRD 正确标注了与 PRD-01（底部导航）的依赖关系。
- PRD 的范围定义明确区分了本 PRD 和 PRD-09（评论）、PRD-10（签到）的边界。
