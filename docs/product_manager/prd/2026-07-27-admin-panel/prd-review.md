## 发现的问题及修正

### R-07：ST-03 中指定 Tailwind CSS 与 Web 端实际技术栈 CSS Modules 冲突

| 属性 | 值 |
|------|-----|
| **编号** | R-07 |
| **维度** | 可落地性 |
| **严重程度** | 🔴 阻塞 |
| **状态** | ✅ 已修正 |

**问题描述**

subtasks.md 中 ST-03 的「管理平台布局」第 4 条写道「样式：Tailwind CSS，白色背景、浅灰边框、无动画」。但 Web 端实际技术栈为 CSS Modules + CSS 自定义属性（tokens），具体证据：

- `web/CLAUDE.md` 明确声明技术栈：`CSS Modules + CSS 自定义属性（tokens）`
- `web/package.json` 没有 `tailwindcss` 依赖
- `web/src/` 中所有组件样式文件均为 `.module.css`（如 `Button.module.css`、`Card.module.css`）
- 项目根 `CLAUDE.md` 规定「新增开源依赖前必须征得用户同意」

如果按照 ST-03 的 Tailwind CSS 方向开发，会导致两种后果：要么引入新依赖并修改 Web 端技术栈声明，要么实现时发现技术栈不匹配需要返工。

**建议修正**

方案 A（推荐，零依赖）：将 ST-03 第 4 条中的「样式：Tailwind CSS」改为「样式：CSS Modules，使用 Design System tokens.css 中的 CSS 自定义属性，保持与现有 Web 端样式体系统一」，并在 Web 技术栈「假设」中注明「使用现有 CSS Modules 体系，不引入 Tailwind CSS」。

方案 B：如果确实想用 Tailwind CSS，需在 PRD 中标注为新增依赖，并获用户同意后更新 `web/CLAUDE.md` 和 `web/package.json`。

**修正记录**

| 轮次 | 日期 | 操作 | 结果 |
|------|------|------|------|
| 2 | 2026-07-27 | ST-03 样式描述改为 CSS Modules + tokens.css（方案 A） | ✅ |

### R-08：Web 端新增 Supabase 依赖未在 PRD 中声明

| 属性 | 值 |
|------|-----|
| **编号** | R-08 |
| **维度** | 可落地性 |
| **严重程度** | 🟡 建议 |
| **状态** | ✅ 已修正 |

**问题描述**

ST-03 依赖 Supabase client SDK 实现登录认证（`onAuthStateChange` 监听登录状态、`signInWithPassword` 登录、`signOut` 退出）。但：

- `web/package.json` 当前不包含 `@supabase/supabase-js` 或 `@supabase/ssr`

**建议修正**

在 PRD 第 5 节「依赖」表中增加一行：`@supabase/supabase-js` / `@supabase/ssr`，类型为「外部依赖」，说明为「Web 端 Supabase Auth 客户端 SDK」，状态为「📅 需征得用户同意后安装」。同时将 Supabase 相关的假设补充到 subtasks.md 工时估算说明中。

### R-09：Admin API 响应格式未定义，与现有 API 格式存在不一致风险

| 属性 | 值 |
|------|-----|
| **编号** | R-09 |
| **维度** | 可落地性 |
| **严重程度** | 🟡 建议 |
| **状态** | ✅ 已修正 |

**问题描述**

Existing Backend API has two response formats: format A (dramas list): `{ data: [...], pagination: { ... } }`, and format B (player series): `{ code: 0, data: {...}, message: "..." }`. ST-02 defines 11 admin API endpoints but doesn't specify which format to use.

**建议修正**

在 subtasks ST-02 中增加 Admin API 响应格式约定：列表类用格式 A，单条 CRUD 和统计用 `{ data: {...} }`，不引入 `{ code, message }` 包装层。

**修正记录**

| 轮次 | 日期 | 操作 | 结果 |
|------|------|------|------|
| 2 | 2026-07-27 | ST-02 API 表后新增「API 响应格式约定」小节，统一定义列表/CRUD/统计三种场景的响应格式 | ✅ |

### R-10：`episode_count` 字段在管理端的更新策略未定义

| 属性 | 值 |
|------|-----|
| **编号** | R-10 |
| **维度** | 完整性 |
| **严重程度** | 🟡 建议 |
| **状态** | ✅ 已修正 |

**问题描述**

Zod Schema 中 `Drama.episode_count` 是 `number.int.min(0)`。管理平台中管理员可通过短剧表单手动编辑，也可通过剧集管理增删剧集，两种路径会导致数据不一致。

**建议修正**

`episode_count` 由后端在 episodes 增删时自动维护（从 episodes 表实时 COUNT），短剧表单不暴露此字段。

**修正记录**

| 轮次 | 日期 | 操作 | 结果 |
|------|------|------|------|
| 2 | 2026-07-27 | ST-02 Drama 管理 API 补充说明：`episode_count` 由后端实时 COUNT 计算，表单不暴露此字段 | ✅ |
